# @spawnforge/ui

## 0.5.0

### Minor Changes

- [#10294](https://github.com/Tristan578/project-forge/pull/10294) [`e4f7782`](https://github.com/Tristan578/project-forge/commit/e4f778238ce90c4770f438de76039d948a8b5d51) Thanks [@Tristan578](https://github.com/Tristan578)! - Modal dialogs now lock page scroll while open. Until now no modal in the app locked scroll on its own; a `body { overflow: hidden }` rule happened to mask this everywhere until PF-1017 ([#9037](https://github.com/Tristan578/project-forge/issues/9037)) correctly scoped it to editor routes, which un-masked the defect on every public page. `Dialog` now uses a new, ref-counted `useScrollLock` hook that locks `document.documentElement` (never `body`, to avoid reopening the exact viewport bug PF-1017 fixed) for as long as at least one dialog is open, and restores the page's prior scroll state only when the last stacked dialog closes. Where the browser draws a classic (space-taking) scrollbar, the lock pads the page by the scrollbar's width so in-flow content does not jump sideways when a dialog opens; `position: fixed` elements anchored to the right edge (such as the cookie banner) are not compensated and still shift by the scrollbar width while a dialog is open.
  
  `useScrollLock(locked: boolean)` is new public API, exported from `@spawnforge/ui` so a hand-rolled overlay can take the same shared, ref-counted lock; that new export is why this is a minor bump for the package. `ScrollArea` now applies `overscroll-behavior: contain` for every consumer, so scrolling past the end of any scroll area no longer scrolls the page behind it, and it accepts a `ref` to its scroll container.
  
  `Dialog`'s body content now renders through `ScrollArea` and the panel is capped at `85dvh` (the visible viewport, so it does not run under a mobile browser's toolbar), so a dialog with tall content scrolls internally instead of growing past the viewport. While that body overflows it is a focusable region named by the dialog title, so keyboard users can Tab to it and scroll it with the arrow keys; when a dialog opens, focus still goes to its first control, not to the scroll region. A dialog with no controls at all focuses the region: the browser reports the overflow only after the first frame, so focus lands on the dialog for a moment and then moves into the region as it appears. If the region stops overflowing while it has focus (a resize or rotation), focus moves to the dialog itself rather than falling out of it, and back into the region if the content overflows again.
  
  `Dialog`'s `actions` footer sits outside that scrolling body (it is marked `data-dialog-actions`), so controls placed there are in view at every scroll offset and never cover the body's content. When a control inside the body takes keyboard focus, the body scrolls it into view (to the nearest edge, and only for keyboard focus, so a mouse press is never moved out from under the pointer); WebKit did not reliably do this on its own for a Tab-focused link.
  
  The quick-start dialog's approval gates no longer put a second scroll box inside the dialog: their summary and the full token cost scroll with the dialog body, and their buttons sit in the dialog's footer, outside that scroll, so the plan is read from the top when the review opens and moving focus between the buttons never scrolls it. In the plan review the footer also shows the token total ("Cost: 340 tokens, up to 400 held", plus "May exceed your balance" when the cached balance looks short), so the number is in view whenever Build it is. Pressing Discard plan turns that row into the confirmation itself: "Discard this plan? Planning it again costs tokens." with Discard it (where Build it was) and Keep plan (where Discard plan was, keeping focus, so pressing it again backs out). A refused Build it brings its reason into view and returns focus to Build it. Discard plan can still be armed while a Build it is starting; its Discard it then cancels that start, and focus goes to Keep plan, never to Discard it. Closing the dialog (Close, Escape or the backdrop) drops an armed Discard, so a reopened review asks nothing and focus is on Build it (or, while that Build it is still starting, on the status line, and back on Build it if the start is refused); when the gate's buttons appear, focus never goes to a destructive one. Reopening the review brings a refusal still held in the store into view again, but not while a Build it is still starting: then Build it stays disabled and the status says the build is starting until that start settles. That hold belongs to the plan being built: a different plan designed after a cancelled build can be built at once, even while the cancelled build is still winding down. A gate that stops a build midway (such as the asset gate) now offers Approve and "Stop build" in that footer, and the dialog's separate Stop button is hidden while it is up, so there is one control for ending the build instead of a "Cancel" and a "Stop" side by side. While a gate's buttons are in the footer, Close is drawn as a secondary (outlined) button, so the gate's own primary button is the only filled one.
  
  The scroll lock and the internally scrolling body are delivered for the shared `Dialog` primitive, together with the quick-start approval-gate rework above (`QuickStartDialog` and `ApprovalGateDialog`, whose gates are split into a summary and an actions group, plus the new `TokenCostTotal`). What is not done is the migration of the ~13 ad-hoc, hand-rolled `fixed inset-0` overlays elsewhere in the app (community/marketplace/dashboard/settings/onboarding): they do not yet consume the `Dialog` primitive and are unaffected, and that migration is tracked separately in [#10297](https://github.com/Tristan578/project-forge/issues/10297).

### Patch Changes

- [#10306](https://github.com/Tristan578/project-forge/pull/10306) [`efb8905`](https://github.com/Tristan578/project-forge/commit/efb8905ebb98b02679d579d8be9a869d73cfdafd) Thanks [@Tristan578](https://github.com/Tristan578)! - Enabled `exactOptionalPropertyTypes` in `web/tsconfig.json` (follow-up to [#7592](https://github.com/Tristan578/project-forge/issues/7592), which enabled it in `apps/docs`, `mcp-server` and `packages/ui`). Fixed every resulting compile error by widening optional fields to explicitly admit `undefined` where the omitted-vs-undefined distinction was already not meaningful to the code reading them (verified case by case against `??`/`?.`/`!== undefined` usage), by conditional-spreading values into vendor types that don't admit an explicit `undefined` (DOM `fetch`/`Response` options, `@ai-sdk/anthropic`, `dockview-react`, `sonner`, Playwright), and by adding a small `omitUndefinedValues` / `LoosePartial<T>` utility pair for patches that may carry an explicit `undefined` key.
  
  Mostly a type-checking change, with these small runtime changes:
  - `set_grid_2d` and `set_physics2d` drop explicit-`undefined` keys from the parsed arguments instead of overwriting the existing grid or physics settings with them (zod keeps an input key that is present with `undefined`).
  - `generationStore.updateJob` drops explicit-`undefined` keys from the patch before merging, so a patch cannot erase a job's `dbId`, `usageId`, `resultUrl` and so on. No caller cleared a field that way.
  - `taskStore.addTask` without a description, and a Twine choice passage with no prompt text, now omit the key instead of storing it with the value `undefined`. Reads see `undefined` either way.
  
  `@spawnforge/ui`: `NumberField`'s `min` and `max`, `Input`'s `error` and `Button`'s `variant` are now typed `T | undefined`, so a consumer compiled with `exactOptionalPropertyTypes` can forward a maybe-undefined value. Passing `undefined` renders the same as omitting the prop (each component already reads them through a destructuring default, `??` or a truthiness check, all of which treat `undefined` and an absent key alike).

## 0.4.0

### Minor Changes

- [#10201](https://github.com/Tristan578/project-forge/pull/10201) [`689ac8d`](https://github.com/Tristan578/project-forge/commit/689ac8d7fb12cafdbbcdd295b74e90dbc562a906) Thanks [@Tristan578](https://github.com/Tristan578)! - Choose how a game counts as complete: Win, Endless, Sandbox or Narrative. Set it from the new Completion mode picker in Scene Settings (keyboard-accessible, with its own Undo and Redo), ask the in-app AI (`set_completion_mode`), or describe a sandbox, endless or story game when generating one. Only Win requires a win condition before Play and generated-game verification pass. A win condition the scene does have is still checked in every mode.   Completion-mode controls follow the active theme and use shared native radio controls with full-option touch targets. AI undo/redo can target completion-mode history explicitly.

- [#8672](https://github.com/Tristan578/project-forge/pull/8672) [`a195378`](https://github.com/Tristan578/project-forge/commit/a1953783e5f81b465b16028eb37638743ec98803) Thanks [@Tristan578](https://github.com/Tristan578)! - fix(ci): align the Node runtime version across the whole monorepo on the canonical major 24.

  The Node version was declared in many drifting places — `.node-version` (24, used by Vercel) disagreed with `.nvmrc` (20), with `engines.node` (`>=20 <25`), and with 31 hardcoded `node-version: 20` inputs to `actions/setup-node` across every GitHub workflow. CI therefore ran on Node 20 while Vercel built on Node 24, the "green in CI, broken on Vercel" footgun (PF-841, [#8665](https://github.com/Tristan578/project-forge/issues/8665)).

  - `.node-version` is now the single source of truth; every `actions/setup-node` step reads it via `node-version-file: .node-version` instead of a hardcoded literal, so there is exactly one place to bump.
  - `.nvmrc` and `engines.node` (`>=24 <25`) now agree, and the previously engines-less workspaces (`apps/docs`, `apps/design`, `packages/ui`) declare `engines.node`.
  - Dropped the now-obsolete `dependabot.yml` ignore that blocked `portless >=0.13.1` "until we adopt Node 24" — that condition is satisfied.
  - A node-environment vitest guard (`web/src/lib/config/__tests__/nodeVersionConsistency.test.ts`) fails CI if any of these sources drift apart again.
