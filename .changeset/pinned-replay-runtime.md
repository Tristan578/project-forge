Runtime input replay now runs on a pinned simulation clock, can be paused, resumed and cancelled, and is available to the in-app AI.

When you replay recorded input in the Playtest panel, the engine's clock is pinned for the duration of the replay: every rendered frame advances the game by exactly one tick (60 per second by default), so the same recording produces the same result whether the editor is running at 15 or 144 frames per second. The clock is released again when the replay finishes, is cancelled, or fails — and stopping Play releases a pin that was in force while playing (a pin made in Edit mode stays until it is unpinned). If the engine cannot pin its clock the replay refuses to run instead of reporting a result that could not be trusted, and the result shows whether the clock was pinned. If the engine declines to release the clock after a finished replay, the verdict still stands and the panel says the clock could not be released.

The Replay button now shows a progress line while a replay runs, with Pause, Resume and Cancel. Pausing releases every key the replay was holding and pauses the game at that tick; resuming picks up the recording where it stopped; cancelling releases the keys, leaves the game running, and records no verdict. Only one replay can run at a time — Record, Replay and Run Playtest wait for a replay started anywhere else, including by the chat assistant — and leaving Play mode cancels whichever replay is in flight, whether it was started by the Replay button, by Run Playtest, or by the assistant. Screen readers hear each change of state at once and the tick position about once a second rather than on every frame.

The AI gameplay bot can now play the running game instead of only rating it: with Play active and the player entity selected, Run Playtest also turns the bot's plan into a recording and replays it through the engine, showing a runtime verdict next to the heuristic report. The chat assistant has a new `replay_input_trace` tool that does the same thing from a recorded trace or a bot strategy; it is refused outside Play mode with the same rule the panel applies. Two engine commands, `pin_frame_rate` and `unpin_frame_rate`, expose the clock pin to agents: `hz` is a rate in ticks per second, 4 to 240 (4 Hz is the floor because the engine clamps any longer step to 250 ms), and the tools report the engine's own answer instead of assuming success.

A game component added in the same engine frame as its entity's spawn is no longer dropped. Spawning is deferred inside the engine, so an `add_game_component` (or a physics or transform update) issued before the next frame could not find its entity and was discarded without a word; the editor's own pipeline happened to wait for the spawn first, which is why this went unnoticed. The engine now carries such a request forward for up to three frames and logs the ones it has to give up on, so a character controller added right after `spawn_entity` takes effect.

The record/replay check against the real engine (`e2e/engine/inputReplay.spec.ts`) is now part of the required per-PR engine gate, including a pause, cancel and restart scenario that must land within 0.01 world units of an uninterrupted run, and its timing limits are asserted on the median of five samples.
