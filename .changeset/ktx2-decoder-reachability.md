"web": patch
---

Texture upload from the editor and the chat assistant, and custom PNG skyboxes, work again; unsupported image formats are refused with a message that names the accepted ones.

Texture loading had been broken in two places at once. The engine read the texture body from a field named `data` while everything in the editor sent `dataBase64`, so every upload failed before it was looked at; and no PNG or JPEG decoder was compiled into the engine, so even a correctly named upload - and every AI-generated skybox, which arrives as PNG - would have failed with "invalid image mime type" in the engine log. Both are fixed: the engine accepts `dataBase64` (and still `data`), and the PNG and JPEG decoders are built in. A test in the engine now fails if the list of accepted formats ever names a format the build cannot decode.

Only PNG and JPEG textures are accepted. A `load_texture` whose data URL declares anything else - `image/ktx2`, DDS, WebP - is refused with "unsupported texture format '<type>'; accepted formats are image/png, image/jpeg", by the editor before the command is sent and by the engine if it is sent anyway; a raw base64 body with no data URL header is typed by its own first bytes (see below). The asset panel, material inspector, sprite inspector and pixel-art editor now send the file's data URL whole, so a JPEG upload reaches the JPEG decoder and a `.webp` file is refused by name instead of being decoded as PNG and failing silently. The chat assistant's `load_texture` tool checks the format before it touches the editor, so it no longer reports "Loading texture" for a file the engine will refuse, and it hands the model the reason.

A glTF or GLB model whose images are KTX2 (declared by `mimeType`, by a data URI's own type, or by a `.ktx2` file name) or that uses `KHR_texture_basisu` is refused before it is queued, as is a file that is not a readable glTF/GLB document; the message names the image and says to convert the model's textures to PNG or JPEG. The existing 50 MB limit on models and textures is unchanged but is now answered to the caller as an error rather than only logged.

Why: the engine's KTX2 path decompresses with a library that has a known unbounded-allocation flaw (RUSTSEC-2026-0344) and cannot be upgraded while the renderer depends on it, so a crafted import could exhaust the importing tab's memory. Neither path crosses a user boundary - a scene stores asset metadata, not the bytes, and the import drains are editor-only - so this closes a problem for the person doing the importing, not a remote one.

The engine's refusal reason is shown in the editor as a persistent notification on every refused file (identical refusals collapse into one), and the AI tools relay it as the tool's error. The MCP manifest and the command reference describe the accepted formats for `load_texture` and the refusal for `import_gltf`.

Dropping or picking a batch in which many files fail now raises at most three of the editor's own notifications - the first two files by name and one summary line - instead of a toast per file, so they fit the visible stack; the rest are listed in the browser console. (A file the engine refuses by format keeps its own persistent notification, as before.) An unreadable model or audio file no longer stops the rest of a drop or leaves the import progress bar stuck. And a failure inside the editor while handing a file to the engine (a thrown store action for a texture, model or audio file) is reported as that, naming the file, rather than as an unreadable file or not at all.

A texture uploaded from the Sprite inspector now actually replaces the sprite's image; before, the engine registered the image and then looked for the sprite's slot on a material, where it does not exist, so the upload did nothing. A model picked or dropped with an upper-case `.GLTF` extension loads, instead of being stored as a `.glb` the loader cannot parse. A raw base64 texture body with no data URL header is accepted as PNG or JPEG by its own first bytes and refused otherwise, with "raw base64 texture data is neither PNG nor JPEG; send a data URL that names image/png or image/jpeg", instead of always being decoded as PNG and failing silently when it was not one. A dropped file of a type the editor does not import (a `.webp`, say) is now named in a notice rather than being dropped without a word. A generated image is typed by its own first bytes before it is placed, whatever content type its storage served, so a PNG or JPEG is no longer refused as unrecognised or handed to the wrong decoder. The same holds wherever else a texture reaches a 2D sprite: a texture imported or dropped in the Asset panel while a sprite is selected, pixel art applied with the pixel art editor's Apply to Sprite, and a generated pixel-art, sprite or tileset image aimed at a sprite with no slot named now replace the sprite's image instead of looking for a material the sprite does not have. A texture picked or dropped with no entity selected is now named in a notice that says to select one, rather than being skipped without a word. And a generated model or texture that completes while the engine is not attached is recorded as not placed, with the reason, rather than as placed.
