Bind generation job ids to the caller so a signed-in user can no longer poll another user's job (#10262).

The `/api/generate/<type>/status` routes that resolve a provider key (model, skybox, sprite, sprite-sheet, texture, tileset-gen, pixel-art; `music/status` resolves none) use the platform provider key by default for a zero-cost status check, so they never verified that the polled `jobId` belonged to the caller. `createGenerationHandler` now binds a just-issued provider job id to the creating user server-side, before the response is returned, and every one of those status routes checks that binding before resolving a key. A confirmed mismatch is refused with 404. If the ownership lookup itself fails (a database error, or the circuit breaker failing fast during an outage), the route still refuses, but with a retryable 503 that the client keeps polling through, so a database blip never fails and refunds a correctly bound job. `POST /api/jobs` also refuses to create a client-reported job row for a `providerJobId` already bound to a different account. The check is keyed on the job id alone, so the client-reported `provider` string cannot bypass it. The refusal is a 404 with the status routes' body, which names neither the owner nor the job's status or result. It does still differ from the 201 an unbound id gets, so a caller holding a foreign job id can learn that some other account has bound it. That is accepted: provider job ids are unguessable provider-issued tokens. A parser-based coverage test reads every App Router route file, in every spelling Next.js serves and at any path, and selects each one that uses a key export of the key resolver: every exported value of that module, derived from its source on each run, except a pinned list of exports that return no key, each pinned to its exact declared return type so that changing one fails the test until it is decided again. It fails one that resolves a key without first checking ownership of the polled `jobId` for the authenticated caller (the same user the key is resolved for), or that reads any other caller input it could send the provider. Imports and globals are whitelisted for the same reason, because either can read the request without a handler argument: such a route may import only `next/server` and the app's own source, with no dynamic `import()` or `require`, and may read only a short list of safe globals (no `process`, `globalThis`, `eval` or `Function`; a `declare` statement, which emits nothing, cannot make one of them local and is itself reported). A route is excused only by a pinned exemption with a stated reason that the test re-checks (a token-charged new operation, a secondary key resolved inside an already-charged generation, or the QStash-signed callback). It also fails any POST route behind a checked route that binds nothing, and fails if any status endpoint the client polls is missing from the routes it reads.

Rollout consequence: a job created before this deploy (or whose ownership bind write failed) has no `provider_job_owners` row, so the owner's own poll answers 404. The client now treats a status-route 404 as terminal. It stops polling and refunds immediately, showing "We lost track of this generation, so it was stopped. Try generating it again.", instead of retrying every 3 seconds for five minutes. Account deletion also removes the user's `provider_job_owners` rows, so the new non-cascading foreign key cannot block right-to-erasure.
