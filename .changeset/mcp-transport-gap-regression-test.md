No behavior change. Added a regression test (`src/transport/__tests__/transportGap.test.ts`) for the `@modelcontextprotocol/sdk` `Transport` type gap tracked in #10278 (`onclose`, `onerror`, `onmessage` and `sessionId` are declared optional without `| undefined` on `Transport` but as `| undefined` on `StreamableHTTPServerTransport`). The test finds the `as Transport` casts in the real `src/transport/http.ts`, recompiles that file with the casts removed under the real `tsconfig.json`, and reads the disagreeing members through the type checker (inherited and alias-typed members included). The un-cast compile alone decides whether the gap has closed: the test tells you to drop both casts only when `http.ts` compiles without them, and reports a broken derivation, not a closed gap, if tsc still errors while no disagreeing member is found. It also fails if a cast is removed, the casts are replaced, a cast is unneeded, or a cast is not applied directly to the SDK transport, and each failure says what it can: a removed cast breaks the baseline compile, reported with the line, the error code and the compiler's message; replacing every cast with something tsc accepts that is not an `as Transport` leaves no cast to find, reported as such (there is no line to name); an unneeded cast is reported with its line and the number of exactOptional errors its removal produced; a cast not applied directly to the SDK transport is reported with its line, the cast text and the operand's type (or the target's type, for a cast to something other than the SDK's `Transport` interface). Overlay cases rewrite the SDK `.d.ts` and `http.ts` text to keep those shapes covered. Verified the SDK still disagrees with itself at the pinned 1.30.0. The `http.ts` comment now lists all four members and points at the test; the two casts are unchanged.
