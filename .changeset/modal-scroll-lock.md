Modal dialogs now lock page scroll while open. Until now no modal in the app locked scroll on its own; a `body { overflow: hidden }` rule happened to mask this everywhere until PF-1017 (#9037) correctly scoped it to editor routes, which un-masked the defect on every public page. `Dialog` now uses a new, ref-counted `useScrollLock` hook that locks `document.documentElement` (never `body`, to avoid reopening the exact viewport bug PF-1017 fixed) for as long as at least one dialog is open, and restores the page's prior scroll state only when the last stacked dialog closes. Where the browser draws a classic (space-taking) scrollbar, the lock pads the page by the scrollbar's width so in-flow content does not jump sideways when a dialog opens; `position: fixed` elements anchored to the right edge (such as the cookie banner) are not compensated and still shift by the scrollbar width while a dialog is open.

`useScrollLock(locked: boolean)` is new public API, exported from `@spawnforge/ui` so a hand-rolled overlay can take the same shared, ref-counted lock; that new export is why this is a minor bump for the package. `ScrollArea` now applies `overscroll-behavior: contain` for every consumer, so scrolling past the end of any scroll area no longer scrolls the page behind it, and it accepts a `ref` to its scroll container.

`Dialog`'s body content now renders through `ScrollArea` and the panel is capped at `85dvh` (the visible viewport, so it does not run under a mobile browser's toolbar), so a dialog with tall content scrolls internally instead of growing past the viewport. While that body overflows it is a focusable region named by the dialog title, so keyboard users can Tab to it and scroll it with the arrow keys; when a dialog opens, focus still goes to its first control, not to the scroll region. A dialog with no controls at all focuses the region: the browser reports the overflow only after the first frame, so focus lands on the dialog for a moment and then moves into the region as it appears. If the region stops overflowing while it has focus (a resize or rotation), focus moves to the dialog itself rather than falling out of it, and back into the region if the content overflows again.

`Dialog`'s `actions` footer sits outside that scrolling body (it is marked `data-dialog-actions`), so controls placed there are in view at every scroll offset and never cover the body's content. When a control inside the body takes keyboard focus, the body scrolls it into view (to the nearest edge, and only for keyboard focus, so a mouse press is never moved out from under the pointer); WebKit did not reliably do this on its own for a Tab-focused link.

The quick-start dialog's approval gates no longer put a second scroll box inside the dialog: their summary and the full token cost scroll with the dialog body, and their buttons sit in the dialog's footer, outside that scroll, so the plan is read from the top when the review opens and moving focus between the buttons never scrolls it. In the plan review the footer also shows the token total ("Cost: 340 tokens, up to 400 held", plus "May exceed your balance" when the cached balance looks short), so the number is in view whenever Build it is. Pressing Discard plan turns that row into the confirmation itself: "Discard this plan? Planning it again costs tokens." with Discard it (where Build it was) and Keep plan (where Discard plan was, keeping focus, so pressing it again backs out). A refused Build it brings its reason into view and returns focus to Build it. Discard plan can still be armed while a Build it is starting; its Discard it then cancels that start, and focus goes to Keep plan, never to Discard it. Closing the dialog (Close, Escape or the backdrop) drops an armed Discard, so a reopened review asks nothing and focus is on Build it; when the gate's buttons appear, focus never goes to a destructive one. Reopening the review brings a refusal that is still on screen into view again, but not while a Build it is still starting: then Build it stays disabled and the status says the build is starting until that start settles. A gate that stops a build midway (such as the asset gate) now offers Approve and "Stop build" in that footer, and the dialog's separate Stop button is hidden while it is up, so there is one control for ending the build instead of a "Cancel" and a "Stop" side by side. While a gate's buttons are in the footer, Close is drawn as a secondary (outlined) button, so the gate's own primary button is the only filled one.

The scroll lock and the internally scrolling body are delivered for the shared `Dialog` primitive, together with the quick-start approval-gate rework above (`QuickStartDialog` and `ApprovalGateDialog`, whose gates are split into a summary and an actions group, plus the new `TokenCostTotal`). What is not done is the migration of the ~13 ad-hoc, hand-rolled `fixed inset-0` overlays elsewhere in the app (community/marketplace/dashboard/settings/onboarding): they do not yet consume the `Dialog` primitive and are unaffected, and that migration is tracked separately in #10297.
