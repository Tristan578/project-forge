# Extended Gotchas Reference

These are lower-frequency gotchas moved from CLAUDE.md. The most common ones remain in CLAUDE.md; these apply in specific contexts.

## Build & CI
- **Verify npm package names with `npm view`** — Hallucinated package names cause silent startup failures.
- **vitest --coverage needs `--coverage.reporter=json-summary`** — Without it, `coverage-summary.json` is never created.
- **Node 25.x segfaults** — intermittent V8 JIT crashes in hooks. Investigate, don't bypass with `--no-verify`.
- **`vercel build` in CI** — can't find npm. Use `vercel deploy` (remote build) instead.
- **Artifact versions** — the v4+ artifact format is cross-compatible, so `upload-artifact` and `download-artifact` do NOT have to share a major: the tree runs `upload-artifact@v7.0.1` + `download-artifact@v8.0.1`, both on the Node24 runtime. The real constraint is the RUNTIME, not the shared major — never pin an artifact action to a major still on the **deprecated Node20** (runners removed Node20 in fall 2026). The old "must match `@v4`" rule is stale. The `upload-artifact` v4(Node20)→v7(Node24) bump is done (#8854, closed).
- **Reusable workflow permissions** — `quality-gates.yml` must use `permissions: contents: read`. Never `write`.
- **Full vitest in worktrees kills M2** — use `npx vitest run <specific-file>` or `npm run test:changed`.
- **Cherry-pick + lockfile** — Always regenerate `package-lock.json` after cherry-picks that touch dependencies.
- **`nodeVersion` is invalid in `vercel.json`** — Configure Node version in Vercel project settings instead.
- **`lhci collect` flags differ from Lighthouse CLI** — Use `--outputDir`, `--numberOfRuns`, `--settings.chromeFlags`.
- **`.lighthouserc.js` auto-detected by lhci** — `startServerCommand` overrides manually-started servers.
- **`next start` requires env vars** — Set `SKIP_ENV_VALIDATION=true` in CI for production mode without full env.
- **Duplicate YAML keys in GitHub Actions are silent** — Two `env:` blocks: first vanishes. Always merge into single block.
- **E2E CI uses `next start` not `next dev`** — `next dev` cold-compiles 2-3 min. Requires `playwright.ci.config.ts`.
- **Sentry/Copilot re-review on every push** — Fix ALL issues in ONE commit, run `security-reviewer` BEFORE pushing.
- **Vitest 4.x jest-dom matcher registration** — Use explicit `expect.extend(matchers)` in vitest.setup.ts.
- **Storybook build target is `es2022`** — `apps/design/vite.config.ts` sets `build.target: 'es2022'`. Do NOT use `esnext` (not a real target) or legacy targets like `safari14` (esbuild 0.28 can't transform destructuring for it). No legacy browser support for internal tooling.
- **`secrets` context forbidden in workflow_call step `if:`** — Use an env var in a prior step and check step outputs instead. GitHub Actions only allows `env`, `github`, `inputs`, `steps` etc. in step conditions inside reusable workflows.
- **Single-root-lockfile monorepo: a `package.json` bump WITHOUT regenerating the ROOT lockfile breaks `npm ci` on main.** There is exactly ONE `package-lock.json` (repo root); `web/package-lock.json` does not exist. Dependabot's npm updater is `directory: /web`, so it edits `web/package.json` but **cannot** relock the root → the manifest range stops matching the pinned lockfile version → every `npm ci` (all of CI + the Quality Gates jobs that run it as setup, e.g. Rust Security Audit, Lighthouse) fails with `EUSAGE Missing: <pkg>@<ver> from lock file`. A caret bump is enough: `^0.12.0`→`^0.13.0` resolves to the newest satisfying version the stale lockfile doesn't carry. Shipped twice (#8655, #8658 → #8683).
  - **Detection:** the `Lockfile Sync` job in `.github/workflows/ci.yml` runs `scripts/check-lockfile-sync.sh`, which regenerates the lockfile from the manifests and fails the PR on any diff — deterministic and pre-merge, unlike `npm ci` which only trips after the bad state lands. It is gated on the ci-gate `needs-deps` output (any `package.json` at any depth, or the root lockfile) and wired into the required `CI Success` aggregate, so it is required when it runs yet skips cleanly on PRs that touch no manifest. The gate's decision logic is unit-tested by the `lockfile-sync-tests` (a.k.a. "CI Self-Defense Tests") job in the same `ci.yml` (also wired into `CI Success`, so neutering the gate fails a required check, not just an advisory one). The `CI Success` verifier (`scripts/check-ci-success.sh`) adds an anti-tamper check — a self-defending gate may not be `skipped` while its trigger fired — which RAISES THE COST of unwiring (a one-line `if: false` no longer suffices) but is defense-in-depth, not an airtight proof: a coordinated multi-file edit could still get past automation, so human review of any `ci.yml` / `scripts/` change remains the backstop. What the automation closes is the silent single-line slip.
  - **Fix any drift:** run `npm install --package-lock-only` from the repo root and commit the updated `package-lock.json`.
  - **After merging ANY dependency PR:** verify `npm ci` against `origin/main` — a Dependabot force-push can leave the last green run reflecting an intermediate (consistent) state, not the final manifest-only squash.
- **Dependabot's last-green CI can lie after a force-push** — a Dependabot PR's green checks may reflect an earlier commit, not the final force-pushed tree. Never merge a Dependabot npm PR on a stale green; re-run the gate against the actual head (`@dependabot rebase` re-evaluates against current main).
- **gh-aw `.lock.yml` drift: edit a `.github/workflows/*.md` source (or a `.github/aw/` action pin) WITHOUT recompiling, and the workflow GitHub runs silently diverges from its source.** GitHub Agentic Workflows compiles each author-edited `.github/workflows/*.md` into a generated sibling `*.lock.yml` ("DO NOT EDIT … run gh aw compile"), injecting SHA-pinned action refs from `.github/aw/actions-lock.json`. The `.lock.yml` is what GitHub actually executes — so a stale lock is the gh-aw analogue of package-lock drift, and the parity review found it live (committed locks pinned a different compiler version than `actions-lock.json`). Four drift vectors, all caught via `git status --porcelain` (NOT `git diff --quiet`, which misses untracked/deleted): (1) a tracked lock recompiles to different content, (2) a NEW source whose lock was never compiled, (3) an orphan lock whose source was deleted (`--purge` removes it), (4) an action-pin bump that changes injected SHAs.
  - **Detection:** the `gh-aw Lock Sync` job in `.github/workflows/ci.yml` runs `scripts/check-ghaw-lock-sync.sh`, which installs the gh-aw compiler pinned to the version recorded in the committed locks (derived by `scripts/get-ghaw-compiler-version.sh` — highest `compiler_version` via `sort -Vu | tail -1`, NOT lexicographic `head -1`, which would pick an older version; note `gh extension install --pin` pins a git TAG, not a content SHA — `gh` has no commit-digest flag, so this buys reproducibility, NOT a supply-chain SHA pin, and does not claim to), recompiles from the committed sources/pins, and fails the PR on any diff. It restores the tree afterward (a check, not a fix). Gated on the ci-gate `needs-ghaw` output (`.github/workflows/*.md|*.lock.yml`, `.github/aw/**`, or the gate's own scripts) and wired into the required `CI Success` aggregate, so it is required when it runs yet skips cleanly otherwise. The gate's decision logic + the version helper are unit-tested by the `lockfile-sync-tests` ("CI Self-Defense Tests") job and shellchecked there — the suite runs hermetically by injecting a stub compiler through the test-only `$GHAW_COMPILE_CMD` seam (never set in CI, where the real `gh aw compile` runs), so it needs neither the gh-aw extension nor the network. The `CI Success` verifier (`scripts/check-ci-success.sh`) anti-tamper forbids skipping the gate while `needs-ghaw` fired — same self-defense pattern as the Lockfile Sync gate (human review of any `ci.yml`/`scripts/` change is still the backstop).
  - **Fix any drift:** from the repo root, FIRST pin your local gh-aw compiler to the exact version the gate uses — a locally-installed gh-aw of any OTHER version recompiles to different bytes and the gate fails with an opaque `git status --porcelain` diff whose real cause (compiler skew) is never named: `ver="$(bash scripts/get-ghaw-compiler-version.sh)"; gh extension remove gh-aw 2>/dev/null || true; gh extension install github/gh-aw --pin "$ver"` (the helper derives the version from the committed locks — the SAME value CI pins to at `ci.yml`'s ghaw-lock-sync install step; the remove-then-install makes the pin idempotent, since `gh extension install` errors if the extension is already present). THEN run `gh aw compile --no-check-update --purge` and commit the updated `.github/workflows/*.lock.yml`. (`--no-check-update` keeps the run offline/deterministic; `--purge` removes orphan locks. Do NOT add `--force-refresh-action-pins` — it re-resolves SHAs from the network, making the gate drift on upstream tag movement rather than contributor error. When you are intentionally BUMPING the compiler rather than fixing drift, pin to the NEW version explicitly — the committed locks still record the old one, so the helper would hand you the version you are trying to move off of.)
  - **Node-version guard exemption:** the gh-aw v0.77.5+ compiler injects its own `actions/setup-node` step (the agent runtime that installs the Copilot CLI) with a literal `node-version` into every generated lock, and its `runtimes:` frontmatter accepts only literal versions — no version-file mode. So `*.lock.yml` files are exempt from the PF-841 node-version-consistency guard (`web/src/lib/config/__tests__/nodeVersionConsistency.test.ts`); the exemption is itself guarded — every excluded lock must carry the `gh-aw-metadata` marker, so an authored workflow can't hide behind the `.lock.yml` suffix.
  - **Dependabot's `github_actions` updater opens un-mergeable PRs against the generated locks — the action pins inside `*.lock.yml` are COMPILER-OWNED, not Dependabot-owned.** `gh aw compile` injects every `uses:` ref (incl. `actions/checkout`, `actions/setup-node`) from the compiler's OWN bundled pin registry, so a Dependabot hand-edit (e.g. `actions/checkout` `v6.0.2`→`v7.0.0` across the five generated locks) can NEVER pass `gh-aw Lock Sync`: recompiling re-emits the compiler's pin → `git status --porcelain` always drifts. Seen live on **#8872** — the only mergeable change there was the one hand-authored `ci.yml` checkout bump; the five lock edits had to be reverted (`git checkout HEAD~1 -- .github/workflows/*.lock.yml`) before the gate went green. Triage such a PR by reverting every `*.lock.yml` edit and keeping ONLY hand-authored workflow/source changes. The DURABLE fix — bump the gh-aw compiler so its bundled pin is current (v0.77.5→v0.81.6, whose registry carries `actions/checkout@v7.0.0`), recompile all five locks, AND scope a `.github/dependabot.yml` `exclude-paths: [".github/workflows/*.lock.yml"]` so the updater stops scanning the generated locks — landed in **#8880 (PF-932)**. Caveat: `exclude-paths` is GA (2025-08-26) but has open upstream bugs where it is occasionally not respected (dependabot-core#13526), so treat churn-suppression as validated only after observing a real Dependabot github-actions run skip the locks; the compiler-owned pin (which always re-emits on recompile) is the real backstop.
- **`npm audit` gate is an ALLOWLIST gate, not raw `--audit-level=high` — and the raw command CANNOT pass on this tree.** Today's un-relockable blocker is `GHSA-mh99-v99m-4gvg` (HIGH, ReDoS) — the root `brace-expansion@1.x` under the eslint-9/minimatch@3 lint toolchain, the gate's sole live waiver, pinned to `node_modules/brace-expansion`. A bare `npm audit --audit-level=high` fails whenever any un-relockable high advisory exists — which is why the gate is allowlist-based, NOT a package.json/lockfile change (that would only churn the Lockfile Sync gate). The gate is strictly TIGHTER than the old raw command: it still blocks all high+critical, waives only explicitly listed advisories — each pinned to its expected `node_modules` location(s) since PF-1009/#9026 — and fails CLOSED (exit 2) on any tooling error. (HISTORY — the cohort that motivated the gate: drizzle-kit (dev-only; `0.31.x` was already the LATEST) transitively bundled an OLD esbuild two ways — a direct `esbuild ^0.25` range AND the DEPRECATED `@esbuild-kit/*` loaders (`@esbuild-kit/esm-loader → @esbuild-kit/core-utils → esbuild ~0.18`). npm 11.x `overrides` provably did NOT cascade into those nested copies (verified across global-range, global-exact, and deeply-nested-scoped override forms) and `--omit=dev` did not prune them (tsx/vite hoist esbuild to the root), so two dev-only, non-exploitable esbuild advisories — `GHSA-gv7w-rqvm-qjhr` high, Deno binary-integrity RCE via `NPM_CONFIG_REGISTRY`, install-time; `GHSA-g7r4-m6w7-qqqr` low, dev-server file read on Windows — could not be relocked away. That cohort exited the tree and its two waivers were pruned in PF-1002/#9007.)
  - **Detection / wiring:** `scripts/check-npm-audit.sh <workspace>` runs in the `Rust Security Audit` job (`.github/workflows/quality-gates.yml`) for `web`, `mcp-server`, AND the repo root (`.`), and again in the deploy security step (`cd.yml`). The root run exists because `npm audit` scopes reported advisories to the INVOKING workspace's dependency subtree even though every invocation loads the identical single-root-lockfile graph — so the `web`/`mcp-server` runs never evaluate the ROOT workspace's own devDeps, nor the `packages/*`/`apps/*` workspaces; auditing from the root covers the entire install graph (PF-1010/#9029 — the gap is STRUCTURAL, not a live finding: at fix time the root run surfaced zero rows unique to it — root and `web` report the IDENTICAL 9 "high" entries, the waived `brace-expansion` source plus 8 eslint-family string-`via` propagation rows — but the root workspace's own devDeps and the `packages/*`/`apps/*` subtrees sit outside both prior invocations' scope, so a future high advisory there would have shipped unaudited; closing the gap needed zero new waivers). It reads `npm audit --json`, evaluates only OBJECT-valued `via` entries (string `via` are pure propagation — covered transitively by waiving the source), and exits 1 on any advisory at/above `FAIL_SEVERITIES` (`high critical`) that is (a) not allowlisted, (b) allowlisted but found at a `node_modules` path outside its pinned set, or (c) allowlisted but reported with no usable `nodes` location data — a waiver that cannot be location-verified is not a waiver. A missing/empty/unrecognized severity is also blocking-eligible (projected to an `unknown` sentinel — a row that cannot be proven below threshold is never silently ignored; every TSV field is sentinel-filled in the jq projection because an EMPTY field would collapse under IFS-whitespace splitting and shift the columns, which pre-fix flipped a BLOCK into a WAIVED exit 0). It exits 2 (fail-closed) on a malformed allowlist entry (bare id / empty path), a non-v2 audit report, a jq extraction failure (including a non-string severity/url/title), or an empty field surviving into the read loop. Decision logic is unit-tested by `scripts/__tests__/check-npm-audit.test.sh` in the `lockfile-sync-tests` ("CI Self-Defense Tests") job — hermetic via the test-only `$NPM_AUDIT_CMD` seam (NEVER set in CI; wiring it in a workflow would no-op the audit, so the suite asserts no executable line in either workflow sets it). The suite also pins the wiring that makes a red audit actually BLOCK: no step-level `if:`/`continue-on-error:` on any audit step, no job-level `if:`/`continue-on-error:` on the quality-gates security job, and no job-level `continue-on-error:` on cd.yml's security job — cd.yml's security job legitimately carries exactly ONE job-level `if:` (main-push/workflow_dispatch only), which the suite pins to that count and to containing `refs/heads/main` rather than pinning it absent (every YAML-key assertion in the suite — count, absence, and containment alike — matches its key through a `["']?` class, because YAML accepts a key in EITHER quote style — `"if":` and `'if':` are the same key as `if:`, and a double-quote-only class left single-quoted duplicates of every pinned key green. The same spelling class bites a SECOND construct that is easy to miss when sweeping the matchers: the awk **terminators** of the job-block cuts. A bare-only terminator (`^  [A-Za-z_][A-Za-z0-9_-]*:`) does not stop at `  'zz-decoy':`, so for a job that is LAST in the file — `ci-success` is — the cut runs to EOF and every pin beneath it reads a FOLLOWING job's keys. That is worse than a false positive: deleting ci-success's `needs:` and appending a single-quoted decoy job carrying `- quality-gates` produced a GREEN suite plus the affirmative line "ci-success still lists quality-gates in its needs: aggregate" while ci-success listed nothing (the bare-key form of the same mutation was already caught, so the quote was the entire ingredient). All six job-level cuts now share one quote-tolerant, colon-REQUIRING terminator (`^  ["']?[A-Za-z_][A-Za-z0-9_-]*["']?[[:space:]]*:`). An intermediate round dropped the colon on the theory that inside `jobs:`, any 2-space letter-initial line IS a job key since properties sit at 4 spaces — that theory is FALSE and dropping it was a regression two review seats caught independently. YAML indentation bounds BLOCK structure, not scalars: a multi-line quoted scalar continues at ANY indentation, including less than its own key's, so `name: "trunc` / `  decoy"` puts a 2-space colonless line INSIDE the job. The colonless class matched it and TRUNCATED the cut, and every pin below then read a block missing the keys it pinned — which fails OPEN, because count pins ("exactly one `steps:`") and absence pins ("no `continue-on-error:`") are satisfied by evidence that was cut away. Strictly worse than the quoted-decoy finding above, which at least turned the required check red: here the appended duplicate `steps:` wins under last-key-wins, every audit is replaced by an echo, and the job still reports SUCCESS. The key-level cuts elsewhere stay colonless SAFELY, and that asymmetry is why the precedent didn't transfer: they host positive containment pins, where truncation removes the NEEDLE and fails closed; only job-level cuts host count/absence pins. Because a continuation can also carry a colon (`  B: 2}`) or be spelled exactly like a bare job key (`  decoy:`), the charset alone is insufficient at any width. An intermediate round tried to close that with two SHAPE-based preconditions — every 2-space line inside `jobs:` looks like a job key, and no line opens an unclosed quoted scalar or flow collection — and both review seats breached the second one within the same round, independently and with different payloads: a backslash-escaped quote (`concurrency: "grp\"`) survives an even-parity quote count while leaving the scalar open, and an opener that isn't shaped `key: value` — a bare sequence item (`- "a`), an anchor (`&a "trunc`), a tag (`!!str "trunc`) — is never examined at all. Each was measured live: suite green, PyYAML confirming a job with `continue-on-error: true` and its whole step list replaced. The lesson is that "does this line LOOK like a job key?" is a blacklist against unbounded YAML spellings, and three successive widenings each traded one spelling for the next. So the suite instead pins the EXACT SET of 2-space lines inside `jobs:` per workflow (11 / 14 / 22 job keys), which is spelling-independent by construction: a continuation, however opened or spelled, is a 2-space line absent from the list. It also covers the reverse direction no shape test did — respelling a REAL job key (`  "security":`) so the terminator stops matching it and the PRECEDING job's cut over-runs into it. It fails closed in every direction (a missed section anchor, an early-ended section, or a grown workflow all yield a mismatch, and an empty enumeration is refused outright rather than passing vacuously — the same discipline `check-openapi-route-sync.sh` applies to an empty route enumeration), and the section anchor is quote-tolerant to match the sibling top-level `jobs:` count pin. That enumeration then turned out to carry the SAME defect one level up, found independently by two review seats with different payloads: the exact set was pinned, but the scan's own BOUNDARY was still inferred line by line (`awk` started at `jobs:` and stopped at the next column-0 line). A quoted scalar continues at ANY indentation INCLUDING column 0 while staying inside a nested job, so the section could be ended from inside a job body and every job key after that point simply never enumerated. At most cut sites that costs the attacker the FOLLOWING job keys and turns the suite red; in the LAST job of a file every key has already printed and the kill is FREE. `ci-success` is last in ci.yml, is a cut target, and hosts a count pin (exactly one `needs:`) that fails OPEN when its block is truncated — measured live at 146/0 green while PyYAML resolved `ci-success.needs == ['ci-gate']` with the `- quality-gates` aggregate gone. Fixed by applying the same discipline to the boundary instead of widening the rule again: the scan now runs to EOF (no boundary rule is load-bearing at all), and the exact ORDERED set of column-0 keys is pinned per workflow (5 / 6 / 5), which inherently pins `jobs` as the LAST top-level key — the premise scanning to EOF rests on. Values are stripped (`name: CI` → `name`) so a cosmetic workflow rename stays green; no column-0 value is load-bearing. A continuation spelled exactly like a real top-level key still lands as an extra ordered element, so the comparison catches it. Cost, by design: adding, renaming or removing a job turns the suite red until the list is updated — a one-line, obviously-correct edit, and for a self-defense suite the prompt is the point. Scope, honestly: this makes the cuts' premise VERIFIED rather than assumed for these three files; it does not make line-based cutting sound in general, and like every pin here a coordinated edit of both the workflow and the suite defeats it, so it raises the cost of textual tampering without claiming to be airtight. Two later rounds extended the same discipline in both directions. First the enumeration's own false-POSITIVE direction: an exact-set comparison mismatches on ANY cosmetic difference, so a trailing comment or trailing whitespace on a genuine job-key line (`  security:  # gate`) reddened the suite over nothing. Both are stripped before comparing — the opposite polarity from the containment assertions below, where a needle alive only inside a comment is tampering; here a comment is noise. Then the RESIDUAL this note used to record — that the pin governed the 2-space JOB-key lines only, while keys INSIDE a job were still matched by bytes through the `["']?` class — turned out to be a LIVE hole, not a theoretical one, and was closed by applying the enumeration one level deeper. YAML 1.2 resolves `\u` escapes inside double-quoted scalars, so `"\u0073teps"` and `steps` are the SAME mapping key to the parser and different byte strings to grep. Appending `"\u0073teps":` plus one `- run: echo pwned` to quality-gates.yml's security job measured 150 PASS / 0 FAIL while PyYAML resolved that job to `steps=1` with ZERO audit steps — all three npm audits and the cargo audit replaced, the job reporting SUCCESS rather than skipped, so the skip-based anti-tamper never fires either. The plain spelling of the identical payload is RED, which is what makes the escape the whole ingredient; an escaped `continue-on-error` and an escaped `needs:` were false green the same way. Fixed by pinning the exact set of 4-space keys in every cut job block, values stripped as at column 0 — no job-level VALUE is load-bearing for THIS pin, and the ones that are load-bearing elsewhere — five of them, not the three an earlier draft of this note listed: the deploy `if:` clause, the audit `run:` lines, the caller's `uses:`, the security job's `name:` (what the branch-protection rule matches on), and ci-success's own job-level `if:` (`always()`, without which the required check SKIPS, and a skipped required check reads as satisfied) — keep their own containment assertions, so a cosmetic job rename stays green. A 4-space continuation from a multi-line scalar carries no colon, survives the strip intact, and lands as an unexpected element; an emptied block is refused outright rather than passing vacuously. All six cut blocks carry it, and the last one earned its place by measurement rather than reasoning: the ci.yml `quality-gates` caller looked like uniformity-only, on the theory that its `uses:` pin is positive containment and so fails closed. It does NOT — an appended escaped `"\u0075ses": ./.github/workflows/decoy.yml` repoints the reusable-workflow call under last-key-wins while the ORIGINAL `uses:` line still satisfies containment, measured green pre-fix with the sole execution site of all three npm audits pointed at a decoy. Scope, as everywhere here: spelling-independent, NOT parser-equivalent — whether GitHub's own workflow parser resolves `\u` escapes the way PyYAML does is not something this suite measures), no job-level `needs:` on EITHER security job (on quality-gates a conditional dependency like `editor-boot` would cascade-skip it and a skipped required check reads as satisfied; on cd.yml a skippable dependency like `build-wasm` — which skips on any non-engine push — would cascade-skip the audit into a deploy-through, since that job's `if:` has no `always()` to rescue it), `security` stays a flow-list element of the `needs:` lists of cd.yml's `deploy-staging` and `deploy-production`, AND each of those deploy jobs' `if:` bodies still contains the explicit `needs.security.result == 'success'` clause (deploy-staging directly, deploy-production in its `workflow_dispatch` promote branch). The clause pin is the load-bearing half of that edge: both deploy `if:` blocks start `always() &&`, under which a FAILED dependency does not skip the dependent job — so `needs:` membership alone blocks nothing (it only makes `needs.security` resolvable), and deleting the one clause line leaves the workflow valid while a red audit no longer stops either deploy. The clause pin matches inside the cut job-level `if:` block ONLY — a needle occurrence elsewhere in the job (an `env:` value, a step name) has no gating effect and does not satisfy it — each deploy job's `if:` key is also count-pinned to exactly one (YAML keeps the last duplicate key, so an appended second `if: always()` would override the clause at runtime while the intact original block still satisfied containment) — and it proves the clause is PRESENT, not that it is EFFECTIVE: a vacuous rewrite like `(needs.security.result == 'success' || true)` still passes, since resisting that would mean parsing GitHub Actions expressions (same raises-cost-not-airtight register as the other anti-tamper checks here). The skipped direction is covered too: `deploy-staging`'s `if:` accepts `needs.security.result == 'skipped'`, and `deploy-production` inherits that exposure on the push path (its push branch gates only on `needs.deploy-staging.result == 'success'`, never on `security` directly) — so a SKIPPED security job would satisfy both deploy gates, and the if:-count/containment and needs:-absence pins above, which keep the security job itself un-skippable, are load-bearing for the same guarantee. (`deploy-docs`/`deploy-design` are NOT audit-gated at all — pre-existing gap, tracked in PF-1011/#9030.) Both security jobs' job-level `steps:` key is count-pinned to exactly one — the severe member of the duplicate-key class: an appended second `steps:` at the end of the job replaces the ENTIRE step list under YAML last-key-wins (all three npm audits + cargo audit gone) while the job exits 0 and reports SUCCESS, not skipped, so the `CI Success` skip-based anti-tamper never fires; on cd.yml a replaced step list additionally makes `needs.security.result == 'success'` genuinely TRUE, satisfying every deploy clause pin on its own terms. The step-scoped textual assertions can't tell which `steps:` key owns the steps they match — with exactly one, the scanned steps ARE the effective steps. Orthogonal to every pin above — which all cover the INSIDE of the gating job — the suite also pins that the workflow CONTAINING it is still INVOKED: `quality-gates.yml` is `workflow_call`-only and is called from exactly one place, ci.yml's `quality-gates:` job, and since cd.yml does not run on `pull_request` at all, that caller is the SOLE execution site for all three npm audits on the PR path. So the caller's JOB key is count-pinned to one, its `uses:` is pinned to `./.github/workflows/quality-gates.yml` (repointing it leaves quality-gates.yml on disk with every pin intact and auditing nothing), and its `if:` is count-pinned to one whose comment-stripped body still contains `needs-any-code` — an `if: false` there leaves the job EXISTING, so ci-success's `needs:` list still resolves and the job merely SKIPS, which `check-ci-success.sh` USED to certify green (it fails only on failure/cancelled). ## Database
- **Always use `queryWithResilience()`** — Only call `getDb()` inside the `queryWithResilience()` callback, never assign it to a standalone variable. Example: `queryWithResilience(() => getDb().select()...)`. ESLint `no-restricted-syntax` flags the `const db = getDb()` assignment pattern across `src/**`.
- **`onConflictDoUpdate` field completeness** — List EVERY mutable field in `.set()`. Missing fields keep original values.
- **Delete children before insert on upsert** — `db.delete(childTable).where(eq(parentId))` before inserting.
- **ZADD member uniqueness** — `Date.now()` collides in same ms. Use `` `${Date.now()}:${Math.random().toString(36).slice(2,8)}` ``.
- **CTE `FOR UPDATE` required for row locking** — Without it, concurrent requests snapshot the same pre-update value.
- **neonSql.transaction must include ALL related writes** — Never split claim and deduction across separate operations.
- **neon-http tagged template returns `Row[]`** — Use `.length` to check results, not `.rowCount`.
- **Circuit breaker trips at 5 consecutive transient failures** — Stays open for 30s, then half-open (1 probe). Non-transient errors (auth, syntax) don't count. Opening fires a Sentry alert (#8244); half-open/closed transitions are silent.
- **PGlite has no pgvector — the `.db.test.ts` harness rewrites vector DDL, so parity is name-existence only (PF-985 / #8977).** `@electric-sql/pglite` 0.5.x does not bundle pgvector, so replaying `drizzle/0010_graph_retrieval_nodes_edges.sql` verbatim throws `extension "vector" is not available` and breaks EVERY `*.db.test.ts` (the whole harness build fails, not just graph tests). `pgliteHarness.ts` `buildSchema()` applies a test-only DDL-rewrite shim before `pglite.exec`: strip `CREATE EXTENSION [IF NOT EXISTS] vector;`, `vector(N)` → `text`, and `USING hnsw (col vector_cosine_ops)` → `USING btree (col)` under the SAME index name (the regex stops at the closing paren so a trailing `WHERE "embedding" IS NOT NULL` partial-index predicate passes through untouched). This keeps table/column/index NAMES real so `schemaMigrationParity.db.test.ts` stays honest, but its scope is explicitly name-existence only — it does NOT diff column types or index predicates. Production keeps the real `vector(1536)` + HNSW; the rewrite never ships. Prod enables the extension via a dedicated `Enable pgvector extension` step in `cd.yml` that runs BEFORE `drizzle-kit push` (push does not emit `CREATE EXTENSION`).

## API & Security
- **usageId in generate route responses** — NEVER remove. Client needs it for async job refunds.
- **`refundTokens()` idempotency** — Check `metadata->>'refundedUsageId'` before crediting.
- **Generate status route: provider-success-with-no-artifact must map to `failed`, not `completed`.** A provider (Meshy/Replicate/Suno) can report success (`SUCCEEDED`/`succeeded`/`completed`) yet produce no downloadable artifact (empty GLB / `{}` maps / no audio URL). Mapping that unconditionally to `status: 'completed'` makes `useGenerationPolling` throw an uncaught "No result URL"/"No texture maps", stick the job in `downloading` for the full 5-min poll cap, then refund only via a generic timeout (#8757/#8758/#8759). Every `/api/generate/*/status` route must gate the result field (`resultUrl`/`maps`/…) on `mappedStatus === 'completed'` and report `failed` — with a specific `<Type> generation produced no <artifact>` message via a `succeededButEmpty` flag — when the artifact is absent (note `Object.keys(maps).length === 0` counts as absent; a truthy `{}` does not). The poller's `handleCompletion` catch also calls `triggerRefund(id)` so any completed-job download/import failure (expired URL, invalid GLB) refunds too, not just the status-route path.
- **`sanitizePrompt().filtered` without `.safe` check** — Always check `.safe` first.
- **Never spread LLM objects into engine commands** — Allowlist fields with `Number.isFinite()` guards.
- **`VERCEL_ENV` includes `'development'`** — Use explicit `=== 'production' || === 'preview'`.
- **`sanitizeSystemPrompt` truncates at 10k chars** — Use inline regex for scene context (can be 50k+).
- **`ToolLoopAgent.stream()` has no `onError`** — Use `result.toUIMessageStreamResponse({ onFinish })`.
- **Dynamic route `[name]` params need validation** — If POST validates name characters, PATCH/DELETE on `[name]` must validate too. Malformed percent-encoding (`%E0%A4%A`) passes Next.js decoding but should return 400 before DB queries.
- **`InstructionBlock[]` cache controls only fire on direct backend** — `createSpawnforgeAgent({ instructions: InstructionBlock[] })` joins blocks into a flat string when `isDirectBackend` is false. Adding `tier: 'long'` does nothing on the gateway/OpenRouter path. Per-user content (e.g. scene context) must include a per-user nonce inside the block text — Anthropic's prompt cache is keyed at the org level, so two users on the same Anthropic key share a cache namespace.
- **Chat SSE is the AI SDK v6 `UIMessageChunk` protocol — HYPHENATED types, v6 field names.** `/api/chat` streams via `result.toUIMessageStreamResponse(...)`, so `chatStore.streamOneTurn` must parse `text-delta {delta}` (NOT `text`), `reasoning-delta {delta}`, `tool-input-available {toolCallId, toolName, input}` (full parsed input — no JSON-string accumulation), `tool-input-error`/`tool-output-error {errorText}`, and a top-level `error {errorText}` (NOT `message`). Usage rides on `finish.messageMetadata.usage` via the route's `messageMetadata` callback — there is no standalone `usage` chunk in v6. Drift between route and client silently blanks every reply and runs zero tools (#8746). `web/src/test/utils/streamingTestUtils.ts` `makeChatSSEEvents` is the canonical wire shape; the parser is tested against exactly those bytes so a future protocol mismatch fails a test instead of shipping.

## Engine & Game Loop
- **Win event is once-guarded on TWO independent flags — keep both** — `game_win` can originate from the engine (native ECS `system_win_condition`) OR a script (`forge.game.win()`). The engine path guards re-fire on `runtime.game_won` (`game_components.rs` — `if condition_met && !runtime.game_won`); the script path guards on the Zustand `gameWon` flag (`useScriptRunner.ts` `case 'game_win'`, re-broadcasts to the worker only `if (!gStore.gameWon)`). The worker's `GAME_EVENT` handler has **NO** dedup of its own. The CanvasArea overlay also gates on `engineMode !== 'edit'` so a stale `gameWon` can't paint over the editor.
- **`GameComponentRuntime` presence IS the play gate** — it's inserted on Edit→Play and removed on Play→Edit. Game-component systems read `Option<ResMut<GameComponentRuntime>>` and early-return when absent rather than reading `EngineMode`. Don't add a redundant mode check.
- **The bridge is wasm32-only, so bridge systems can't be unit-tested natively** — `engine/src/lib.rs` gates `pub mod bridge` behind `#[cfg(target_arch = "wasm32")]`; native `cargo test` never compiles it. ## Enforcement Hooks
- **`block-deferred-fixes.sh` fails closed** — If body extraction fails, the hook BLOCKS (exit 2), not allows (exit 0). Previous behavior silently let unparseable replies through.
- **Subagent hook inheritance gap** — `.claude/settings.json` PreToolUse hooks do NOT fire for subagents. The `block-deferred-fixes.sh` hook only catches the main agent. Subagents must self-enforce via the banned-phrase list embedded in `/resolve-pr-comments` SKILL.md.
- **Bare SHA is not enough** — A reply must contain BOTH a commit SHA AND an action verb ("Fixed in", "Addressed in"). A reply like "Good catch abc1234" is blocked — it has a SHA but no action verb, so it's likely deferred-fix language with an unrelated hex string.
- **`#NNNN` ticket reference is acceptable** — A deferred reply with a real GitHub issue number (#8307) is allowed. The rule is "fix it or track it", not "fix it or die".
- **60+ deferred-fix phrases** — The hook checks for phrases like "known limitation", "out of scope", "low-priority", "acceptable tradeoff", "future refactor" in addition to the obvious "will fix later" family. Full list in `.claude/hooks/block-deferred-fixes.sh`.
