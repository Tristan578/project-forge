# Extended Gotchas Reference

These are lower-frequency gotchas moved from CLAUDE.md. The most common ones remain in CLAUDE.md; these apply in specific contexts.

## Build & CI
- **Verify npm package names with `npm view`** — Hallucinated package names cause silent startup failures.
- **vitest --coverage needs `--coverage.reporter=json-summary`** — Without it, `coverage-summary.json` is never created.
- **Node 25.x segfaults** — intermittent V8 JIT crashes in hooks. Investigate, don't bypass with `--no-verify`.
- **`vercel build` in CI** — can't find npm. Use `vercel deploy` (remote build) instead.
- **Artifact versions** — the v4+ artifact format is cross-compatible, so `upload-artifact` and `download-artifact` do NOT have to share a major: the tree runs `upload-artifact@v7.0.1` + `download-artifact@v8.0.1`, both on the Node24 runtime. The real constraint is the RUNTIME, not the shared major — never pin an artifact action to a major still on the **deprecated Node20** (runners removed Node20 in fall 2026). The old "must match `@v4`" rule is stale. The `upload-artifact` v4(Node20)→v7(Node24) bump is done (#8854, closed).
- **Reusable workflow permissions** — `quality-gates.yml` must use `permissions: contents: read`. Never `write`.
- **Full vitest in worktrees kills M2** — use `npx vitest run <specific-file>` or `npm run test:changed`.
- **Cherry-pick + lockfile** — Always regenerate `package-lock.json` after cherry-picks that touch dependencies.
- **`nodeVersion` is invalid in `vercel.json`** — Configure Node version in Vercel project settings instead.
- **`lhci collect` flags differ from Lighthouse CLI** — Use `--outputDir`, `--numberOfRuns`, `--settings.chromeFlags`.
- **`.lighthouserc.js` auto-detected by lhci** — `startServerCommand` overrides manually-started servers.
- **`next start` requires env vars** — Set `SKIP_ENV_VALIDATION=true` in CI for production mode without full env.
- **Duplicate YAML keys in GitHub Actions are silent** — Two `env:` blocks: first vanishes. Always merge into single block. **The same last-key-wins rule is a live neutering vector against every self-defense suite that pins a gate with a containment grep**: appending a second `run:` to a gate step (or a second job-level `if: false`) replaces the effective value while the original line stays byte-present, so `grep -qF 'run: bash scripts/<gate>.sh'` still passes and the suite reports green on a dead gate. On the `pull_request` path GitHub runs the PR's OWN workflow file, so the mutation takes effect in the very run that should have caught it, and `actionlint` (which would flag it) is not wired into this repo's CI. The fix is a **count pin** — materialize the block, `grep -c` the key anchored to its indent level (job keys at exactly 4 spaces; `run:` scoped to a step cut), require exactly 1 — now applied across `check-lockfile-sync`, `check-openapi-route-sync`, `check-ghaw-lock-sync`, `check-native-bindings` and `check-ci-success` (#9031). Full rationale, the already-covered inventory, the three-guard step-cut awk, and why the idiom is duplicated per suite rather than shared: `docs/guides/npm-audit-gate-hardening.md` → "Sibling suites: the duplicate-key count pin".
- **E2E CI uses `next start` not `next dev`** — `next dev` cold-compiles 2-3 min. Requires `playwright.ci.config.ts`.
- **The five-command local gate (`eslint` + `tsc` + `vitest`) structurally CANNOT see an RSC boundary violation — only `next build` can.** A React Server Component that transitively reaches a client-only module (`useSyncExternalStore`, a Zustand store, a `use client` hook) fails the build with `You're importing a component that needs "X". That only works in a Client Component` — and nothing else in the tree reports it. `tsc` type-checks the import fine, ESLint has no rule for it, and vitest resolves every module in a single non-RSC graph. Shipped live: `physicsProfileExecutor.ts` did `await import('@/stores/editorStore')`, the executor barrel is reachable from `app/api/game/decompose/route.ts`, and that one edge dragged `hooks/useEngine.ts` into a server route and reddened **9 CI checks** off ONE root cause (PF-1118 / #9192 — the Lighthouse gate is not independent, it runs its own `next build`).
  - **Turbopack traces DYNAMIC imports too.** `await import('…')` is a real module edge, not an escape hatch. A **type-only** import (`import type`, or an inline `import('…').Foo` in type position) is erased and safe.
  - **The gate rule:** run `SKIP_ENV_VALIDATION=true NODE_OPTIONS=--max-old-space-size=8192 npm run build` before pushing ANY change that adds an import edge into `lib/` code reachable from an API route. The `NODE_OPTIONS` bump is not optional on Node 25 — the default ~2GB heap OOMs and surfaces as the opaque `Next.js build worker exited with code: null and signal: SIGABRT`, which reads like a crash rather than a memory limit.
  - **The durable fix is not to remember, it's to invert the dependency.** Pass a live getter through the context (`getStore: () => useEditorStore.getState()`, supplied by the client-only orchestrator) instead of importing the store from the shared module. A function carries no module edge. `web/src/lib/game-creation/__tests__/serverSafeImports.test.ts` then makes the mistake a unit-test failure: it scans every non-test source file under `lib/game-creation` for a value-import of `@/stores/` or `@/hooks/useEngine`. Note its comment-stripper must be quote-aware and its type-only exemption must NOT match `await import(…).then(…)` — both were live holes when it was written.
- **Sentry/Copilot re-review on every push** — Fix ALL issues in ONE commit, run `security-reviewer` BEFORE pushing.
- **Vitest 4.x jest-dom matcher registration** — Use explicit `expect.extend(matchers)` in vitest.setup.ts.
- **Storybook build target is `es2022`** — `apps/design/vite.config.ts` sets `build.target: 'es2022'`. Do NOT use `esnext` (not a real target) or legacy targets like `safari14` (esbuild 0.28 can't transform destructuring for it). No legacy browser support for internal tooling.
- **`secrets` context forbidden in workflow_call step `if:`** — Use an env var in a prior step and check step outputs instead. GitHub Actions only allows `env`, `github`, `inputs`, `steps` etc. in step conditions inside reusable workflows.
- **Single-root-lockfile monorepo: a `package.json` bump WITHOUT regenerating the ROOT lockfile breaks `npm ci` on main.** There is exactly ONE `package-lock.json` (repo root); `web/package-lock.json` does not exist. Dependabot's npm updater is `directory: /web`, so it edits `web/package.json` but **cannot** relock the root → the manifest range stops matching the pinned lockfile version → every `npm ci` (all of CI + the Quality Gates jobs that run it as setup, e.g. Rust Security Audit, Lighthouse) fails with `EUSAGE Missing: <pkg>@<ver> from lock file`. A caret bump is enough: `^0.12.0`→`^0.13.0` resolves to the newest satisfying version the stale lockfile doesn't carry. Shipped twice (#8655, #8658 → #8683).
  - **Detection:** the `Lockfile Sync` job in `.github/workflows/ci.yml` runs `scripts/check-lockfile-sync.sh`, which regenerates the lockfile from the manifests and fails the PR on any diff — deterministic and pre-merge, unlike `npm ci` which only trips after the bad state lands. It is gated on the ci-gate `needs-deps` output (any `package.json` at any depth, or the root lockfile) and wired into the required `CI Success` aggregate, so it is required when it runs yet skips cleanly on PRs that touch no manifest. The gate's decision logic is unit-tested by the `lockfile-sync-tests` (a.k.a. "CI Self-Defense Tests") job in the same `ci.yml` (also wired into `CI Success`, so neutering the gate fails a required check, not just an advisory one). The `CI Success` verifier (`scripts/check-ci-success.sh`) adds an anti-tamper check — a self-defending gate may not be `skipped` while its trigger fired — which RAISES THE COST of unwiring (a one-line `if: false` no longer suffices) but is defense-in-depth, not an airtight proof: a coordinated multi-file edit could still get past automation, so human review of any `ci.yml` / `scripts/` change remains the backstop. What the automation closes is the silent single-line slip.
  - **Fix any drift:** run `npm install --package-lock-only` from the repo root and commit the updated `package-lock.json`.
  - **After merging ANY dependency PR:** verify `npm ci` against `origin/main` — a Dependabot force-push can leave the last green run reflecting an intermediate (consistent) state, not the final manifest-only squash.
- **A lockfile can be INTERNALLY INCONSISTENT — recorded ranges correct, resolved nodes stale — and `npm install --package-lock-only` will NOT fix it.** Distinct from the drift above and invisible to a regen-and-diff gate. The workspace entry records the NEW range (`.packages["web"].devDependencies["@playwright/test"] = "^1.62.1"`) while the resolved node still carries the OLD version (`.packages["web/node_modules/@playwright/test"].version = "1.62.0"`). npm reads the recorded ranges, concludes the manifests are already satisfied, and **re-resolves nothing** — so the regeneration is a genuine no-op, `git diff` is empty, and the gate reports "in sync" on a lockfile that makes frozen `npm ci` fail with `EUSAGE Missing: <pkg>@<ver> from lock file`. Shipped on **#9070** (PF-1049): every gate green, Vercel's preview build was the only thing that caught it. A LOCAL `npm ci` also passes in this state whenever `node_modules` is already populated ("up to date in 1s") — a warm cache satisfies every edge while the committed file is broken, so a green local install proves nothing.
  - **Detection:** stage 1 of `scripts/check-lockfile-sync.sh` runs `npm ls --package-lock-only --all --json` **before** the regen/diff stage (order is load-bearing — stage 2 mutates the file in place, so checking after it would grade npm's output instead of what the PR ships) and reports every unsatisfied edge in the `problems` array. `--package-lock-only` is what makes it read the LOCKFILE rather than the installed tree.
  - **Do NOT key on npm's exit code, and do NOT text-match `/invalid/`.** `overrides` in the root `package.json` deliberately force versions outside declared ranges, and npm reports every one as `invalid` — the HEALTHY committed lockfile yields **8 problems and a permanent exit 1** (postcss, @clerk/shared, sharp, undici, esbuild, dompurify, js-cookie, ws — all override entries). A gate red on every PR gets deleted, not fixed. Text-matching fails too: `character-reference-invalid` is a real transitive package here. The signal is the problem set **minus** the packages `overrides` forces, derived from `package.json` on every run (self-maintaining, no baseline file to rot). Accepted blind spot: a package both overridden and genuinely drifted is not reported — that is the semantics of an override.
  - **Fix when it fires:** delete the stale nodes, then renormalize — `jq '.packages |= with_entries(select(.key | test("(^|/)node_modules/<pkg>(/|$)") | not))' package-lock.json > /tmp/l.json && mv /tmp/l.json package-lock.json && npm install --package-lock-only`, then verify with a real `npm ci` (`rm -rf node_modules` first, or the warm cache lies).
- **`npm install --package-lock-only` rewrites lockfile platform metadata on SOME npm versions — the local Lockfile Sync gate then reports drift on a clean `main`.** Measured on one macOS host against clean `main`: npm **11.10.0** (bundled with Node 25.6.1) **drops the `"libc"` field from 34 Linux-only optional native-binding nodes** (`@img/sharp-*`, `@next/swc-linux-*`, `@rolldown/binding-linux-*`, `@tailwindcss/oxide-linux-*`, `lightningcss-linux-*`) — 0 nodes added, 0 removed, 0 version/resolved/integrity changes. npm **11.16.0** (bundled with Node 24.18.0, which `.node-version` pins and CI resolves) → **zero drift**. The control that isolates the variable: npm 11.16.0's CLI run **under Node 25.6.1** → also **zero drift**. So this is **npm-VERSION skew — NOT a macOS artifact and NOT a Node-version artifact.** (Do not conflate it with the separate full-`npm install` relock footgun that drops ~91 entries outright and floats pinned roots; under `--package-lock-only` nothing is lost, only metadata rewritten.)
  - **Why it had to be fixed rather than tolerated:** the gate printed `Lockfile drift detected` plus the remediation `npm install --package-lock-only` — which is the very command that produced the diff, so re-running reproduced it forever. It blamed the contributor for damage the toolchain did, with an opaque diff and an unactionable fix.
  - **Detection:** stage 3 of `scripts/check-lockfile-sync.sh` classifies the difference before reporting it. It compares the INDEX copy (`git show :package-lock.json` — the right baseline, since `git diff` compares worktree against index) with the regenerated file after stripping `os`/`cpu`/`libc` from every `.packages` node. Identical after the strip → **exit 2** (fail-closed tooling error, the house convention), naming the running npm, the `.node-version` pin, and a remediation that works. Anything else → the pre-existing **exit 1** contributor-drift path, unchanged. When real drift and the rewrite co-occur, the verdict is exit 1 and the report flags which part of the diff is noise.
  - **This cannot mask real drift.** A manifest change makes npm re-resolve, which adds/removes nodes or changes `version`/`resolved`/`integrity` — all of which survive the strip. `integrity` pins the exact tarball, so a given version can never legitimately change its own platform metadata. The classifier is strictly additive: anything it cannot positively prove benign (including unparseable input) falls through to exit 1. Pinned by `scripts/__tests__/check-lockfile-sync.test.sh` (metadata-only → 2; version/resolved/integrity/node-added/node-removed/top-level-field → 1; noise **plus** real drift → 1).
  - **`npm update … --package-lock-only` strips `libc` even on the "clean" npm 11.16.0 — the zero-drift measurement above is specific to `npm install`.** Measured while relocking for PF-1063 (#9100) under Node 24.18.0 / npm 11.16.0, i.e. exactly the `.node-version` pin: a scoped `npm update nanoid js-yaml dompurify --package-lock-only` produced the 5 intended `version`/`resolved`/`integrity` changes **plus the same 34 `libc` deletions**. So the trigger is the SUBCOMMAND as well as the npm version, and "I used the pinned toolchain" is not on its own a reason to trust a relock diff. Because a scoped `npm update` is the house-recommended relock (a full `npm install` relock drops ~91 native entries outright), this hits every dependency-fix PR.
    - **It does NOT self-report as the metadata-only case.** Stage 3's classifier only returns exit 2 when the diff is *entirely* platform metadata; a real relock always carries version changes too, so the mixed diff lands on the exit-1 contributor-drift path with the `libc` noise flagged but not separated for you.
    - **What to do:** after any `npm update … --package-lock-only`, diff the lockfile **field-by-field against `HEAD`** (not by eyeballing `git diff --stat`) and confirm the only changes are the nodes you meant to move. Restore any stripped `libc` before committing — e.g. reverse-apply just the pure-`libc` hunks — then prove the result round-trips by staging it and re-running `bash scripts/check-lockfile-sync.sh` (its regen must come back byte-identical). Committing the strip makes CI's regeneration re-add all 34 fields and fails Lockfile Sync on a lockfile that is otherwise correct.
    - **`scripts/check-lockfile-sync.sh` restores `package-lock.json` from the INDEX, not the worktree.** Run it against an unstaged relock and it silently reverts your work to `HEAD` — and then passes, because it is now grading the reverted file. `git add package.json package-lock.json` **before** invoking it, and re-check the worktree version afterward.
  - **Fix when it fires locally:** regenerate under the pinned Node — `nvm use` (or `fnm use`/`volta pin`, anything honouring `.node-version`) then `npm install --package-lock-only`. **Never commit the rewritten lockfile to silence it.** If it ever fires in CI, the runner's npm has drifted from `.node-version` — fix the pin.
  - **The "npm 11.16.0 → zero drift" measurement is not reproducible on a populated tree.** Re-measured for PF-1063: a full `npm install --package-lock-only` on Node 24.18.0 / npm 11.16.0 — the exact `.node-version` pin — stripped `libc` from the same 34 nodes (102 deletions, 0 insertions). The one variable that differed from the original clean-`main` measurement is that `node_modules` had just been populated by a real `npm ci` on darwin/arm64, where those Linux-only optional nodes are absent. Treat the npm version as **one** input, not the whole story: verify any relock diff field-by-field regardless of which npm produced it.
- **An `overrides` block in a WORKSPACE `package.json` is silently inert — npm honours `overrides` only from the root manifest.** `web/package.json` carried an eight-entry `overrides` block for its whole life and not one entry ever took effect; six duplicated root entries (so the tree looked correct for the wrong reason) and two were unique and simply unenforced. There is no warning, no lint, and nothing in `npm ls` that reveals it — the block reads as a security control in review while doing nothing.
  - **Proof, if you need to re-derive it:** set the workspace override to something the tree provably violates (`"path-to-regexp": "6.3.0"` against a resolved 8.4.2), run `npm install --package-lock-only`, and observe the resolved version stay at 8.4.2 with no output. A root override with the same value re-resolves immediately.
  - **Consequence for gate reasoning:** `scripts/check-lockfile-sync.sh` derives its override-exclusion set from the **root** `package.json`, so a workspace-level override is invisible to it too — a stale entry there can never be caught by the regen/diff gate, because it was never applied in the first place.
  - **Fix:** put every override in the root `package.json`. Deleting a workspace `overrides` block is a guaranteed lockfile no-op (that is the whole point) — if a delete *does* move the lockfile, npm changed behaviour and the removal needs re-review. Landed for `web/` in PF-1063 (#9100); the two unique entries were `path-to-regexp` (real intent, migrated to root) and a `next-intl.typescript: "$typescript"` entry that was doubly dead — the root declares no `typescript` for `$typescript` to reference, and `next-intl` has no `typescript` dependency or peerDependency to override.
- **Dependabot's last-green CI can lie after a force-push** — a Dependabot PR's green checks may reflect an earlier commit, not the final force-pushed tree. Never merge a Dependabot npm PR on a stale green; re-run the gate against the actual head (`@dependabot rebase` re-evaluates against current main).
- **gh-aw `.lock.yml` drift: edit a `.github/workflows/*.md` source (or a `.github/aw/` action pin) WITHOUT recompiling, and the workflow GitHub runs silently diverges from its source.** GitHub Agentic Workflows compiles each author-edited `.github/workflows/*.md` into a generated sibling `*.lock.yml` ("DO NOT EDIT … run gh aw compile"), injecting SHA-pinned action refs from `.github/aw/actions-lock.json`. The `.lock.yml` is what GitHub actually executes — so a stale lock is the gh-aw analogue of package-lock drift, and the parity review found it live (committed locks pinned a different compiler version than `actions-lock.json`). Four drift vectors, all caught via `git status --porcelain` (NOT `git diff --quiet`, which misses untracked/deleted): (1) a tracked lock recompiles to different content, (2) a NEW source whose lock was never compiled, (3) an orphan lock whose source was deleted (`--purge` removes it), (4) an action-pin bump that changes injected SHAs.
  - **Detection:** the `gh-aw Lock Sync` job in `.github/workflows/ci.yml` runs `scripts/check-ghaw-lock-sync.sh`, which installs the gh-aw compiler pinned to the version recorded in the committed locks (derived by `scripts/get-ghaw-compiler-version.sh` — highest `compiler_version` via `sort -Vu | tail -1`, NOT lexicographic `head -1`, which would pick an older version; note `gh extension install --pin` pins a git TAG, not a content SHA — `gh` has no commit-digest flag, so this buys reproducibility, NOT a supply-chain SHA pin, and does not claim to), recompiles from the committed sources/pins, and fails the PR on any diff. It restores the tree afterward (a check, not a fix). Gated on the ci-gate `needs-ghaw` output (`.github/workflows/*.md|*.lock.yml`, `.github/aw/**`, or the gate's own scripts) and wired into the required `CI Success` aggregate, so it is required when it runs yet skips cleanly otherwise. The gate's decision logic + the version helper are unit-tested by the `lockfile-sync-tests` ("CI Self-Defense Tests") job and shellchecked there — the suite runs hermetically by injecting a stub compiler through the test-only `$GHAW_COMPILE_CMD` seam (never set in CI, where the real `gh aw compile` runs), so it needs neither the gh-aw extension nor the network. The `CI Success` verifier (`scripts/check-ci-success.sh`) anti-tamper forbids skipping the gate while `needs-ghaw` fired — same self-defense pattern as the Lockfile Sync gate (human review of any `ci.yml`/`scripts/` change is still the backstop).
  - **Fix any drift:** from the repo root, FIRST pin your local gh-aw compiler to the exact version the gate uses — a locally-installed gh-aw of any OTHER version recompiles to different bytes and the gate fails with an opaque `git status --porcelain` diff whose real cause (compiler skew) is never named: `ver="$(bash scripts/get-ghaw-compiler-version.sh)"; gh extension remove gh-aw 2>/dev/null || true; gh extension install github/gh-aw --pin "$ver"` (the helper derives the version from the committed locks — the SAME value CI pins to at `ci.yml`'s ghaw-lock-sync install step; the remove-then-install makes the pin idempotent, since `gh extension install` errors if the extension is already present). THEN run `gh aw compile --no-check-update --purge` and commit the updated `.github/workflows/*.lock.yml`. (`--no-check-update` keeps the run offline/deterministic; `--purge` removes orphan locks. Do NOT add `--force-refresh-action-pins` — it re-resolves SHAs from the network, making the gate drift on upstream tag movement rather than contributor error. When you are intentionally BUMPING the compiler rather than fixing drift, pin to the NEW version explicitly — the committed locks still record the old one, so the helper would hand you the version you are trying to move off of.)
  - **Node-version guard exemption:** the gh-aw v0.77.5+ compiler injects its own `actions/setup-node` step (the agent runtime that installs the Copilot CLI) with a literal `node-version` into every generated lock, and its `runtimes:` frontmatter accepts only literal versions — no version-file mode. So `*.lock.yml` files are exempt from the PF-841 node-version-consistency guard (`web/src/lib/config/__tests__/nodeVersionConsistency.test.ts`); the exemption is itself guarded — every excluded lock must carry the `gh-aw-metadata` marker, so an authored workflow can't hide behind the `.lock.yml` suffix.
  - **Dependabot's `github_actions` updater opens un-mergeable PRs against the generated locks — the action pins inside `*.lock.yml` are COMPILER-OWNED, not Dependabot-owned.** `gh aw compile` injects every `uses:` ref (incl. `actions/checkout`, `actions/setup-node`) from the compiler's OWN bundled pin registry, so a Dependabot hand-edit (e.g. `actions/checkout` `v6.0.2`→`v7.0.0` across the five generated locks) can NEVER pass `gh-aw Lock Sync`: recompiling re-emits the compiler's pin → `git status --porcelain` always drifts. Seen live on **#8872** — the only mergeable change there was the one hand-authored `ci.yml` checkout bump; the five lock edits had to be reverted (`git checkout HEAD~1 -- .github/workflows/*.lock.yml`) before the gate went green. Triage such a PR by reverting every `*.lock.yml` edit and keeping ONLY hand-authored workflow/source changes. The DURABLE fix — bump the gh-aw compiler so its bundled pin is current (v0.77.5→v0.81.6, whose registry carries `actions/checkout@v7.0.0`), recompile all five locks, AND scope a `.github/dependabot.yml` `exclude-paths: [".github/workflows/*.lock.yml"]` so the updater stops scanning the generated locks — landed in **#8880 (PF-932)**. Caveat: `exclude-paths` is GA (2025-08-26) but has open upstream bugs where it is occasionally not respected (dependabot-core#13526), so treat churn-suppression as validated only after observing a real Dependabot github-actions run skip the locks; the compiler-owned pin (which always re-emits on recompile) is the real backstop.
- **`npm audit` gate is an ALLOWLIST gate, not raw `--audit-level=high` — and as of PF-1046 the allowlist is EMPTY.** `ALLOWED_ADVISORIES=()` ships with zero entries: every advisory ever waived here was eventually relocked away and pruned (the two esbuild ids in PF-1002/#9007, `GHSA-mh99-v99m-4gvg` brace-expansion in PF-1045 relock + PF-1046 prune). A bare `npm audit --audit-level=high` would therefore pass TODAY — the gate stays allowlist-based because the waiver seam has to already exist the next time an un-relockable high lands, or the only lever left is turning the gate off; and a waiver must be addable without a package.json/lockfile edit (which would only churn the Lockfile Sync gate). **Empty is the correct steady state — do NOT add an entry back "to get the pipeline green".** Always try relocking FIRST: `npm view <pkg> versions` plus the advisory's patched range. "Un-relockable" is a claim about a moment, not a property of a dependency — it expires silently the day upstream backports and nothing re-checks it, which is exactly how the brace-expansion waiver (justified as "patched ONLY in 5.0.8, no 1.x backport exists") kept waiving green after upstream shipped 1.1.17. Both the gate and its suite pin the emptiness: the suite fails if a `"GHSA-` entry reappears, and the three `${ALLOWED_ADVISORIES[@]+"${ALLOWED_ADVISORIES[@]}"}` read guards are load-bearing — under `set -u`, bash 3.2 (macOS system bash) aborts on a plain `"${ARR[@]}"` expansion of an empty array, and because that abort happens inside a command substitution the crashed capture reads back empty and scores as WAIVED, i.e. it fails OPEN. The gate is strictly TIGHTER than the old raw command: it still blocks all high+critical, waives only explicitly listed advisories — each pinned to its expected `node_modules` location(s) since PF-1009/#9026 — and fails CLOSED (exit 2) on any tooling error. (HISTORY — the cohort that motivated the gate: drizzle-kit (dev-only; `0.31.x` was already the LATEST) transitively bundled an OLD esbuild two ways — a direct `esbuild ^0.25` range AND the DEPRECATED `@esbuild-kit/*` loaders (`@esbuild-kit/esm-loader → @esbuild-kit/core-utils → esbuild ~0.18`). npm 11.x `overrides` provably did NOT cascade into those nested copies (verified across global-range, global-exact, and deeply-nested-scoped override forms) and `--omit=dev` did not prune them (tsx/vite hoist esbuild to the root), so two dev-only, non-exploitable esbuild advisories — `GHSA-gv7w-rqvm-qjhr` high, Deno binary-integrity RCE via `NPM_CONFIG_REGISTRY`, install-time; `GHSA-g7r4-m6w7-qqqr` low, dev-server file read on Windows — could not be relocked away. That cohort exited the tree and its two waivers were pruned in PF-1002/#9007.)

## Database
- **Always use `queryWithResilience()`** — Only call `getDb()` inside the `queryWithResilience()` callback, never assign it to a standalone variable. - **`onConflictDoUpdate` field completeness** — List EVERY mutable field in `.set()`. Missing fields keep original values.
- **Delete children before insert on upsert** — `db.delete(childTable).where(eq(parentId))` before inserting.
- **ZADD member uniqueness** — `Date.now()` collides in same ms. Use `` `${Date.now()}:${Math.random().toString(36).slice(2,8)}` ``.

Guarded by `web/src/app/__tests__/public-scroll.test.ts`, which checks EVERY top-level `html`/`body` block (appending a later block is how the cascade reintroduces it), `packages/ui/src/tokens/theme.css` (`@import`ed by globals.css), and the `<body className>` in `app/layout.tsx` (a Tailwind `overflow-hidden` there does the same thing).
- **Full-viewport locks must be `h-dvh`, not `h-screen`.** `h-screen` is `100vh`, which on mobile Safari/Chrome resolves to the LARGE viewport (URL bar retracted). A `100vh` box in normal flow therefore overflows the visual viewport by the browser-chrome height and the surface becomes document-scrollable. `body { overflow: hidden }` used to mask this; nothing does now. `ViewportLock` and `EditorLayout`'s two roots all use `h-dvh` (pinned by the same test).
- **A CSP with neither a nonce nor `'unsafe-inline'` silently blanks the page — Next.js bootstraps App Router hydration with INLINE `<script>` tags.** `/play` shipped `script-src 'self' 'wasm-unsafe-eval'` and every published game rendered a blank/stuck page in production: the server HTML painted, every `self.__next_f.push(...)` bootstrap script was blocked, hydration never ran, and NOTHING threw server-side (PF-1018 / #9038). A CSP tightening that looks correct in review is only proven by a real browser load — `curl` sees the server HTML and reports success on a page no user can use.
  - **The nonce is a THREE-part contract, and each part fails silently alone.** (1) The proxy mints the nonce and sets it on the forwarded REQUEST via `NextResponse.next({ request: { headers } })` as BOTH `x-nonce` and `content-security-policy`, plus the enforcing `Content-Security-Policy` on the response. (2) Next.js reads the nonce off the *request* CSP header to stamp its OWN framework/bootstrap scripts — so dropping that request header, not just the response one, is what re-breaks hydration. (3) App-authored inline `<script>` tags are NOT auto-stamped; the page must read `(await headers()).get('x-nonce')` itself. A static `next.config.ts` `headers()` rule can never carry a per-request value, so the proxy is the only possible minter.
  - **Strip BOTH CSP header names from client input, not just the enforcing one.** Next resolves the nonce as `headers['content-security-policy'] || headers['content-security-policy-report-only']` (`app-render.js`), so leaving report-only unstripped lets a caller smuggle in a nonce of their choosing and have Next stamp it onto every framework script.
  - **`Buffer` is NOT a guaranteed global in the Edge runtime — use `btoa`.** The bare global came from a webpack `ProvidePlugin` (`webpack-config.js`, gated on `isClient || isEdgeServer`); Next 16 builds production with Turbopack, which never runs webpack plugins. Next's Edge sandbox exposes Buffer only through the `node:buffer` `NativeModuleMap`, i.e. via explicit import. A bare `Buffer.from(...)` in middleware is a latent `ReferenceError` that would 500 every request on that path.
  - **`type="application/ld+json"` is a CSP data block, not executable script** — `script-src` never gates it, so JSON-LD needs no nonce (verified in production: un-nonced ld+json tags produce zero violations). Don't cite it as evidence a nonce is working.
  - **A nonce forces dynamic rendering**, which is why the statically-cached marketing pages keep `'unsafe-inline'` instead. Only add a nonce to a route that is already dynamic (`/play` awaits `safeAuth()`).
  - **Repro against a PRODUCTION build, never `next dev`** — the dev server keeps `'unsafe-eval'`/inline for Fast Refresh, so the bug is invisible: `cd web && npm run build && npx next start`, then load `/play/<userId>/<slug>` in a real browser and check for CSP violations in the console.

## Engine & Game Loop
- **Win event is once-guarded on TWO independent flags — keep both** — `game_win` can originate from the engine (native ECS `system_win_condition`) OR a script (`forge.game.win()`). The engine path guards re-fire on `runtime.game_won` (`game_components.rs` — `if condition_met && !runtime.game_won`); the script path guards on the Zustand `gameWon` flag (`useScriptRunner.ts` `case 'game_win'`, re-broadcasts to the worker only `if (!gStore.gameWon)`). The worker's `GAME_EVENT` handler has **NO** dedup of its own. So any NEW system that emits `game_win` MUST set/respect its origin's guard, or `onWin` handlers + the "You Win!" overlay can multi-fire. The CanvasArea overlay also gates on `engineMode !== 'edit'` so a stale `gameWon` can't paint over the editor.
- **`GameComponentRuntime` presence IS the play gate** — it's inserted on Edit→Play and removed on Play→Edit. Game-component systems read `Option<ResMut<GameComponentRuntime>>` and early-return when absent rather than reading `EngineMode`. Don't add a redundant mode check.
- **The bridge is wasm32-only, so bridge systems can't be unit-tested natively** — `engine/src/lib.rs` gates `pub mod bridge` behind `#[cfg(target_arch = "wasm32")]`; native `cargo test` never compiles it. To test logic that the bridge drains (e.g. `emit_game_events_system`), extract the testable core into `core/` (e.g. `GameComponentRuntime::take_pending_events()`) and unit-test THAT natively; the bridge call becomes a thin wrapper. `emit_event` is a JS-callback no-op under native test.
- **`dispatchCommand` returns `void`, so a payload the engine rejects OR silently mangles produces NO signal anywhere — not an exception, not a log, not a failed test.** This is a whole defect CLASS, not one bug (PF-1097, PF-1109, PF-1111, PF-1115, PF-1118 are all instances). It has three distinct shapes, and a change can hit any of them without a single red test:
  - **Hard reject.** The payload fails `serde_json::from_value` and the command is dropped before it is ever queued. `PhysicsData` had no `#[serde(default)]`, so a 3-of-13-field `update_physics` was a hard deserialization failure — the tool call "succeeded", the entity never changed. Likewise `difficultyToCommands()` emitted `update_game_component` with no `componentType`, which the engine rejects outright.
  - **Wrong wire shape.** The keys deserialize to `None` and the command becomes a destructive no-op. `applyPhysicsProfile` sent `speed`/`jumpHeight`/`gravityScale` FLAT, but the engine reads `payload.get("properties")` — a missing `properties` yielded `{}` → a bare `CharacterControllerData::default()` → `gc.add(...)` silently RESET the controller a previous pipeline step had configured.
  - **Undetectable typo.** A partial-update command must be all-`Option` for a partial payload to be legal, and `#[serde(deny_unknown_fields)]` is INCOMPATIBLE with the `#[serde(flatten)]` such payloads use. So `gravtiyScale` deserializes to `None` and no-ops. **The engine structurally cannot close this — the guard has to live on the TypeScript side.**
  - **The guard is pick-based construction, NOT a type annotation.** `{ entityId, ...input } satisfies UpdatePhysicsPayload` is INERT: TypeScript's excess-property (freshness) check applies to properties written literally, never to properties introduced by a spread — and annotating the variable instead is inert for the same reason. Both type-check happily while carrying keys the engine drops. Build the payload key-by-key from an allowlist instead; `web/src/lib/physics/updatePhysicsPayload.ts` is the reference implementation. Its `satisfies Record<keyof PhysicsData, true>` on an OBJECT is bidirectional (an invalid key fails excess-property, an omitted one fails missing-property); `as const satisfies readonly (keyof T)[]` on an ARRAY only proves the keys are valid, never that the list is complete. Read `patch[key]` behind `Object.hasOwn` — a bare read walks the prototype chain and would forward values the caller never set.
  - **`expect.objectContaining` is why this class survives the suite.** It asserts what IS present and is blind to the invented fields sitting alongside. Assert the FULL payload shape (`toEqual`) on every dispatch whose payload IS its behaviour; replacing `objectContaining` here strengthens the suite and is not test weakening.
  - **Still unfixed, same bug:** `handle_set_2d_collider_shape` / `handle_set_2d_body_type` do the identical destructive full-replace and need a `Physics2dPatch`.

## Enforcement Hooks
- **`block-deferred-fixes.sh` fails closed** — If body extraction fails, the hook BLOCKS (exit 2), not allows (exit 0). Previous behavior silently let unparseable replies through.
- **Subagent hook inheritance gap** — `.claude/settings.json` PreToolUse hooks do NOT fire for subagents. The `block-deferred-fixes.sh` hook only catches the main agent. Subagents must self-enforce via the banned-phrase list embedded in `/resolve-pr-comments` SKILL.md.
- **Bare SHA is not enough** — A reply must contain BOTH a commit SHA AND an action verb ("Fixed in", "Addressed in"). A reply like "Good catch abc1234" is blocked — it has a SHA but no action verb, so it's likely deferred-fix language with an unrelated hex string.
- **`#NNNN` ticket reference is acceptable** — A deferred reply with a real GitHub issue number (#8307) is allowed. The rule is "fix it or track it", not "fix it or die".
- **Two hooks can each be correct and jointly unsatisfiable — check the OTHER hooks on the same tool before adding a constraint.** `block-main-commits.sh` refuses to analyse a Bash command over 4000 chars and directs large content to a file; `check-pr-metadata.sh` used to grep only the COMMAND STRING for `Closes #NNNN`, and its own comment admitted it "catches inline `--body` but not `--body-file`". Together they made any substantive PR body unsubmittable: inline was too long to allow, and `--body-file` could never satisfy the `Closes` check. Both hooks passed their own tests; nothing tested the pair. It shipped and blocked the PF-1051 PR (PF-1052). Fixed by teaching `check-pr-metadata.sh` to extract the path from `--body-file <path>` / `--body-file=<path>` / `-F <path>` (quoted or not) and read THAT file.
  - **When a body file is present it is the only thing gh sends, so it alone decides** — a `Closes #NNNN` sitting elsewhere in the command (in `--title`, say) must not launder a linkless body file. Fails closed on a missing/unreadable/directory path or a flag with no value: an unverifiable body is not a verified one.
  - **A blocking hook MUST write its reason to STDERR — the harness surfaces stderr on exit 2, so a reason echoed to stdout arrives as "No stderr output" and the block reads as a mystery instead of a policy.** `check-pr-metadata.sh` printed a full diagnostic to stdout and was silent from the caller's side for its whole life. Wrap the message block in `{ ... } >&2` — the convention `block-main-commits.sh` already documents. Pinned by a `check_err` assertion per blocking path.
  - **A `--title` that MENTIONS a flag is indistinguishable from the flag itself to a grep-based hook.** These hooks cannot parse shell quoting, so first-occurrence extraction pulled the path `so` out of the title `read --body-file so the PR metadata check is satisfiable` — this hook's own PR title — and blocked on it. Scan EVERY occurrence and take the first that names a readable file, falling back to the first occurrence so a command with no usable path still fails closed.
  - **Piping a variable into `grep -q` is SIGPIPE-unsafe under `set -o pipefail`** — `grep -q` exits on first match, SIGPIPEs the writer, and the pipeline reports failure, INVERTING the verdict of a negated test. Use a here-string instead. Latent while commands stay under the pipe buffer; free to remove. `.claude/hooks/__tests__/check-pr-metadata.test.sh` carries a structural guard against reintroducing the pattern.
- **60+ deferred-fix phrases** — The hook checks for phrases like "known limitation", "out of scope", "low-priority", "acceptable tradeoff", "future refactor" in addition to the obvious "will fix later" family. Full list in `.claude/hooks/block-deferred-fixes.sh`.
