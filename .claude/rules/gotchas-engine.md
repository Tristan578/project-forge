# Gotchas — Engine & Game Loop

## Engine & Game Loop
- **Win event is once-guarded on TWO independent flags — keep both** — `game_win` can originate from the engine (native ECS `system_win_condition`) OR a script (`forge.game.win()`). The engine path guards re-fire on `runtime.game_won` (`game_components.rs` — `if condition_met && !runtime.game_won`); the script path guards on the Zustand `gameWon` flag (`useScriptRunner.ts` `case 'game_win'`, re-broadcasts to the worker only `if (!gStore.gameWon)`). The worker's `GAME_EVENT` handler has **NO** dedup of its own. So any NEW system that emits `game_win` MUST set/respect its origin's guard, or `onWin` handlers + the "You Win!" overlay can multi-fire. The CanvasArea overlay also gates on `engineMode !== 'edit'` so a stale `gameWon` can't paint over the editor.
- **`GameComponentRuntime` presence IS the play gate** — it's inserted on Edit→Play and removed on Play→Edit. Game-component systems read `Option<ResMut<GameComponentRuntime>>` and early-return when absent rather than reading `EngineMode`. Don't add a redundant mode check.
- **`system_character_controller` has TWO live movement paths, and a change made to one silently does nothing on the other (PF-1214).** Before the fix it had one: add straight onto `Transform.translation`, which is why there was no gravity, no ground contact, no collision response, and a jump that was a tween the player could hold forever. It now drives Rapier's `KinematicCharacterController` when one is attached — but the legacy direct-translation branch is still reached by **2D projects** and by any 3D character **with no collider** (physics disabled, so Rapier has nothing to sweep). Neither branch errors when it lacks a feature the other has, so "I added a dash and it works" is a claim about ONE branch until you have checked which fixture your test built.
  - **The controller is attached by a lifecycle system, and its ordering edge is load-bearing.** `manage_character_controller_lifecycle` queries `With<Collider>`, and the collider is inserted by `manage_physics_lifecycle` in the same schedule — so without the explicit `.chain()` between them (which is what inserts the `ApplyDeferred` flush) the character sees no collider and every 3D player falls back to the legacy path. It also has to run SECOND so its kinematic `RigidBody` and `LockedAxes` are the ones that survive. Bevy gives an unchained pair no edge at all: the resolution is stable-but-unspecified, so a repeated test run will not surface it.
  - **Rapier's `grounded` is ONE FRAME STALE by construction** — `update_character_controls` runs in `PostUpdate` and resets `controller.translation` to `None` after each step, so an `Update` system reads last frame's `KinematicCharacterControllerOutput`. `step_character` therefore refills the jump budget only when `input.grounded && vertical_velocity <= 0.0`; without the velocity guard the stale flag refills it on the frame right after take-off and every jump is a double jump.
  - **Rapier CLAMPS a blocked move and reports the clamp, but never writes it back into your velocity — so a jump that meets a ceiling keeps its whole upward speed and glides along the underside for the entire ascent (~0.8s / ~48 frames at the default `jumpHeight` of 8.0).** There is no "hit a ceiling" flag; the only signal is `desired_translation` vs `effective_translation` on `KinematicCharacterControllerOutput`, and before PF-1214 nothing in the engine read either field. `character_controller::vertical_motion_blocked` is the predicate, fed in at the `system_character_controller` call site. Three things about it are load-bearing: it is **fraction-based** (`VERTICAL_BLOCK_FRACTION = 0.5`), because the skin width, a grazing wall contact and the slide projection all shave a little off a legitimate rise and an exact comparison would kill every jump taken next to a wall; it has an **epsilon floor**, because a `dt≈0` frame requests a vertical move the size of float noise and comparing noise against a fraction of itself decides nothing; and it is **upward-only**, because a refused DOWNWARD move is the floor, which `grounded` already owns — cancelling it would defeat `GROUND_STICK_VELOCITY` and make `snap_to_ground` let go on ramp seams. The clamp inside `step_character` sits AFTER the grounded bookkeeping (so zeroing the velocity can never be mistaken for a landing that refills the jump budget) and BEFORE the jump gating (the report is last frame's, so a jump accepted THIS frame has to beat a stale block).
  - **A character with no collider is not rejected by the lifecycle — it is never considered, which used to be completely silent.** `CharacterAttachTargets` is filtered `With<Collider>`, and colliders only ever arrive from `manage_physics_lifecycle`'s `With<PhysicsEnabled>` query, so "no collider" means "physics was never enabled on this entity" — the exact PF-1214 golden-path break, since the generation pipeline is what fails to enable it. The entity then keeps the legacy raw-translation path and walks through walls in a scene that looks healthy from every angle. The lifecycle now runs a second query over that negative case and, on a 3D Edit→Play, emits a `tracing::warn!` naming each such entity AND records them in a `CharacterControllerDiagnostics` resource (`commands.insert_resource`, so it needs no registration and is readable from a bare-`World` test). It is written even when empty, so "nothing was skipped" is distinguishable from "the lifecycle never ran"; 2D is never recorded because it uses the legacy path by design. `EntityId` is read as an `Option` so a character missing one is still reported under its Bevy entity — requiring the component would filter it out of the query and reintroduce the same silence one entity at a time.
  - **Slope/step/snap limits are engine-side constants, deliberately NOT `CharacterControllerData` fields.** Adding a serde field there is a multi-file act — `#[serde(default)]`, the TS wire translation in `lib/engine/gameComponentWire.ts`, its textual Rust-parsing test, the inspector and the component checklist. Do that when a game genuinely needs per-character tuning, not to make a number configurable on principle.
  - **The grounded flag reaches JS through a changes-only event, not the play-tick wire.** `CHARACTER_GROUNDED_CHANGED` carries a diff (`core::character_controller::diff_grounded`, native-tested; the bridge wrapper is thin because the bridge is wasm32-only and cannot be unit-tested). A character that DISAPPEARS is reported as `false` rather than dropped — otherwise a consumer that only ever saw `true` keeps a stale "grounded" forever. The browser mirror (`web/src/lib/scripting/groundedRegistry.ts`) is a `Map`, and the worker reads behind `Object.hasOwn`: the id comes off the engine wire, so a plain object answers `isGrounded('constructor')` with an inherited function and lets a script stand on a prototype.
  - **`web/src/lib/scripting/forgeTypes.ts` is ONE template literal.** A backtick inside a doc comment terminates the string mid-file. It fails loudly (tsc and eslint both refuse to parse), but the reported error is a stray `',' expected` a hundred lines away from the backtick, which reads as anything but the real cause.
- **The bridge is wasm32-only, so bridge systems can't be unit-tested natively** — `engine/src/lib.rs` gates `pub mod bridge` behind `#[cfg(target_arch = "wasm32")]`; native `cargo test` never compiles it. To test logic that the bridge drains (e.g. `emit_game_events_system`), extract the testable core into `core/` (e.g. `GameComponentRuntime::take_pending_events()`) and unit-test THAT natively; the bridge call becomes a thin wrapper. `emit_event` is a JS-callback no-op under native test.
- **`dispatchCommand` returns `void`, so a payload the engine rejects OR silently mangles produces NO signal anywhere — not an exception, not a log, not a failed test.** This is a whole defect CLASS, not one bug (PF-1097, PF-1109, PF-1111, PF-1115, PF-1118, PF-1123, PF-1126, PF-1140, PF-1141, PF-1147, PF-1167, PF-1170, PF-1178 are all instances). It has several distinct shapes, and a change can hit any of them without a single red test:
  - **Hard reject.** The payload fails `serde_json::from_value` and the command is dropped before it is ever queued. `PhysicsData` had no `#[serde(default)]`, so a 3-of-13-field `update_physics` was a hard deserialization failure — the tool call "succeeded", the entity never changed. Likewise `difficultyToCommands()` emitted `update_game_component` with no `componentType`, which the engine rejects outright.
  - **Wrong wire shape.** The keys deserialize to `None` and the command becomes a destructive no-op. `applyPhysicsProfile` sent `speed`/`jumpHeight`/`gravityScale` FLAT, but the engine reads `payload.get("properties")` — a missing `properties` yielded `{}` → a bare `CharacterControllerData::default()` → `gc.add(...)` silently RESET the controller a previous pipeline step had configured.
  - **Undetectable typo.** A partial-update command must be all-`Option` for a partial payload to be legal, and `#[serde(deny_unknown_fields)]` is INCOMPATIBLE with the `#[serde(flatten)]` such payloads use. So `gravtiyScale` deserializes to `None` and no-ops. **The engine structurally cannot close this — the guard has to live on the TypeScript side.**
  - **Command that is not the engine's at all.** A fourth shape, and the only one no payload discipline can catch: the command NAME belongs to the browser. A cutscene dialogue keyframe emits `start_dialogue`, which lives in `stores/dialogueStore.ts` and which the engine has never known — handed to the engine dispatcher, it hit `Err("Unknown command: …")` and every authored dialogue beat in every cutscene played through as a silent gap (PF-1140). Since PF-1098 the `tracked` wrapper in `editorStore.ts` calls `reportCommandRejected()` on `success: false`, so this is no longer invisible — but a console error plus a Sentry breadcrumb is a DEVELOPER signal, not a played beat, and an observed rejection is still not a handled command. **Route at the composition root, not inside the producer:** `lib/cutscene/dispatch.ts` wraps the engine dispatcher at the `play_cutscene` call site, so `player.ts` stays a pure command builder. The pin that keeps it honest walks every command `buildCommand` can emit for every `CUTSCENE_TRACK_TYPES` entry and fails unless each is routed locally OR matched by an engine `pub fn dispatch` arm — scoped to those bodies (a whole-file `.rs` scan matches quoted payload VALUES like `"mask"`/`"high"`/`"toggle"` as if they were command names) and minus arms delegating to a handler that only returns "<name> is not implemented" (`set_camera`, `update_scene`, `list_shaders` — matched, then nothing).
  - **`route_domain` is a SECOND, independent gate in front of every handler — a perfect arm the router does not name is dead code.** `core/commands/mod.rs`'s `pub fn dispatch` runs the json guard, then `match route_domain(command)`, where the fallthrough is `_ => 255` and the outer `_` arm answers `Err("Unknown command: …")`. So reachability needs BOTH a non-stub arm in a domain module AND membership in `route_domain`, and the second requirement had never been checked by anything. Sixteen implemented `sprites::dispatch` arms were unroutable, which took the whole 2D tilemap surface (`TilemapInspector`, `TilemapLayerPanel`, eight AI tools in `handlers2d.ts`) plus most of 2D skeletal animation offline — with complete, correct handlers sitting behind them (PF-1178). Two of the sixteen show the nastiest variant: **a name can be routed to the WRONG domain, where a stub shadows a real implementation.** `set_animation_state_machine` / `remove_animation_state_machine` were routed to domain 4, whose arms were inline `Not yet implemented`, while `sprites.rs` held working handlers. That is invisible to a name-only scan on EITHER side, because both sides have the name — only comparing the router's index against the implementing module's index finds it, which is why PF-1175 was filed as "engine stubs, implement them" when the engine work already existed.
    - **The gate is `engine/src/core/commands/mod.rs`'s `#[cfg(test)] mod route_domain_parity`.** It `include_str!`s all twelve domain sources, slices each `pub fn dispatch` body, extracts quoted lower-snake names in match-arm position, and asserts `route_domain(name)` equals that module's own index. Comparing INDICES rather than membership is the whole point. Fails closed: a per-file arm floor, a total floor, a probe that quoted payload VALUES (`"mask"`, `"high"`) are not scored as command names, and a two-direction staleness check on `DELIBERATELY_UNROUTED` (an entry that becomes routed fails; so does one that stops being an arm).
    - **`route_domain` is NOT `pub`** — it is `fn route_domain(command: &str) -> u8`. Any parser must match on `fn`, not `pub fn`; an `awk '/pub fn route_domain/,/^}/'` range silently returns EMPTY, which reads as "no names found" rather than as a broken parser.
    - **Membership in `route_domain` is a UNIVERSAL requirement — there is no exempt set.** The engine-mode/query names handled inline in `dispatch` itself (`play`, `stop`, `get_mode`, `get_camera_state`, …) are listed there too, mapping to domain 12, so a scanner needs no hardcoded special cases.
    - **The TypeScript side must check membership too, and `web/src/stores/slices/__tests__/commandArmParity.test.ts` did not — a false PASS inside the very test written to stop this class.** It scored `set_tileset`, `remove_tileset`, `set_tilemap_data` and `remove_tilemap_data` as reachable on the strength of a non-stub arm alone. It now parses `fn route_domain` and intersects, keeping the subtraction under assertion (`armedButUnrouted` has a floor test plus a named case) so it cannot quietly stop subtracting. The index-vs-index half stays on the Rust side, where `route_domain` can actually be called.
    - **The inverse case is a separate, milder bug, and it is now pinned too.** Twenty names the router sent to a domain with no arm for them (`get_all_reverb_zones`, `create_tileset`, `solve_ik2d`, `set_tile`, `extrude_faces`, …) produced a real `Unknown <domain> command` error, so they only bit a caller who believed the name existed. Most were near-misses of real arms — `set_skeleton_skin2d` vs `set_skeleton2d_skin`, `solve_ik2d` vs `create_ik_chain2d`, `create_tileset`/`update_tileset`/`delete_tileset` vs `set_tileset`, `set_tile` vs `paint_tile` — which is how the vocabulary drifted. All twenty are DELETED (PF-1181); **do NOT alias**, an alias doubles the vocabulary that has to stay in step, which is the root cause. `every_routed_name_has_an_arm_in_its_domain` in `route_domain_parity` now fails the build on a new one. Domain 12 needs no exemption: the check reads `mod.rs`'s own inline `dispatch` arms, so a name dropped from that match still fails instead of being waved through. The `DELIBERATELY_ARMLESS` seam exists and is EMPTY — that is the correct steady state, and an entry there is checked in both directions so it cannot rot.
    - **A routed, armed name whose arm answers `Not yet implemented` is a THIRD state, and neither parity direction can see it** — both sides have the name, so both are satisfied. `get_joint_2d` / `list_joints_2d` sat that way for their whole life, leaving 2D joint state with no read path at all while the 3D surface had two (PF-1194). The Rust-side `an_unrouted_name_is_rejected_by_the_real_dispatch` idiom is what catches it: dispatch the name for real and assert the error is NOT a stub message. Under native `cargo test` a query command errors with `PendingCommands resource not initialized`, which proves BOTH gates passed and the arm queued real work — a stub returns its own string and fails the assertion.
      - **Do not copy the 3D `get_joint` arm.** It ignores its `entityId` and answers `QueryRequest::ListJoints`, i.e. every joint in the scene, which no caller reading the name would expect. And extract a required id explicitly, not with the neighbouring `payload.get("entityId")?` idiom: that `?` returns `None` from the domain `dispatch`, which the router reports as `Unknown physics command` — a malformed payload then looks exactly like a name the engine has never had, the precise diagnosis this whole class exists to prevent.
      - **`pending.query_requests.drain(..).filter(..)` in a query-handling system silently destroys every OTHER system's pending queries.** `drain(..)` empties the whole queue; the `filter` then keeps only the requests this system owns and the rest are gone. `bridge::physics::handle_physics2d_query` did exactly that, so whichever frame ran it first discarded the game-component, game-camera, 2D-skeleton and both joint reads. Nothing surfaces it — an unanswered query is indistinguishable from one whose entity has no data. The correct idiom is `PendingCommands::take_queries(|r| matches!(..))` (`core/pending/query.rs`), which returns the matching requests in queue order and leaves every other variant untouched. Do NOT hand-roll the equivalent `iter().filter(..).cloned().collect()` plus `retain(|r| !matches!(..))`: besides being the two-statement form that is easy to get half-right, `every_deferred_query_variant_is_claimed_by_a_bridge_system` recognises a claim only by parsing `take_queries(` call predicates, so a hand-rolled drain reads to the gate as a variant with no owner and fails the build.
      - **`bridge::query::process_query_requests` is the DEFAULT drain, and its `remaining` list is what lets a dedicated system exist at all.** A variant not named there is drained and dropped by the default system before its own handler ever runs, however correct that handler is — `Physics2dState`, `GameComponentState`, `GameCameraState` and `Skeleton2dState` all had dedicated systems and were being eaten (fixed in PF-1194). Adding a `QueryRequest` variant with its own system means adding it to `remaining` in the same commit, and `every_deferred_query_variant_is_claimed_by_a_bridge_system` (`core/pending/query.rs`) fails the build in BOTH directions: a variant deferred with no `take_queries` claim, and a variant a bridge system claims that `remaining` does not name. The second is the direction PF-1194 shipped broken, and the one an `unclaimed`-only assertion cannot see. `SpriteState` and `Camera2dState` are now deferred (PF-1194), answered by a dedicated system in `bridge/sprite.rs`; the `ProjectType` variant was deleted outright. Variants with no handler anywhere (`AnimationClipState` alone, today) stay in the dropped set on purpose: retaining an unanswerable request leaks the queue unboundedly.
      - **A per-entity read should reply on the channel the store already parses.** `get_joint_2d` answers on the existing `JOINT2D_CHANGED` event rather than inventing a second single-joint wire shape, so `hooks/events/physicsEvents.ts` needed no new parser. Only the list answer (`QUERY_JOINTS2D_LIST`) is new — and a list payload is a JSON ARRAY, which the hub's blanket cast to `Record<string, unknown>` has always misdescribed. A handler that can receive one declares `EventPayload` (`hooks/events/types.ts`) and narrows with `Array.isArray` BEFORE its switch, so every `castPayload` case below still reads a real object. The 3D `QUERY_JOINTS_LIST` had been emitted with no TS listener at all for its whole life — the same dead-vocabulary shape in the inbound direction — and is wired in the same branch. It narrows to `setPrimaryJoint` rather than mirroring the list, because `physicsSlice` holds no per-entity 3D joint record; a selection ABSENT from the list has no joint, so the answer must write `null` there rather than leave a stale one on screen.
  - **Look up a command name with `Object.hasOwn`, never a bare read.** A dispatch table is a plain object, so `TABLE['constructor']`/`['toString']` resolve to inherited functions and a command named for one would be "handled" by `Object.prototype`. The same hazard applies to any id read out of a `Record` — `dialogueTrees['__proto__']` is `Object.prototype`, truthy, and the store's own `tree.nodes.find(...)` then throws on it. That throw is not contained: `CutscenePlayer.tick` schedules the next frame AFTER dispatching, so an exception escaping the dispatcher stops the rAF loop mid-cutscene with `isPlaying` true and no completion callback — only a reload recovers. Wrap local routes in try/catch for that reason.
  - **The guard is pick-based construction, NOT a type annotation.** `{ entityId, ...input } satisfies UpdatePhysicsPayload` is INERT: TypeScript's excess-property (freshness) check applies to properties written literally, never to properties introduced by a spread — and annotating the variable instead is inert for the same reason. Both type-check happily while carrying keys the engine drops. Build the payload key-by-key from an allowlist instead; `web/src/lib/physics/updatePhysicsPayload.ts` is the reference implementation. Its `satisfies Record<keyof PhysicsData, true>` on an OBJECT is bidirectional (an invalid key fails excess-property, an omitted one fails missing-property); `as const satisfies readonly (keyof T)[]` on an ARRAY only proves the keys are valid, never that the list is complete. Read `patch[key]` behind `Object.hasOwn` — a bare read walks the prototype chain and would forward values the caller never set.
  - **`expect.objectContaining` is why this class survives the suite.** It asserts what IS present and is blind to the invented fields sitting alongside. Assert the FULL payload shape (`toEqual`) on every dispatch whose payload IS its behaviour; replacing `objectContaining` here strengthens the suite and is not test weakening.
  - **A serde enum of struct variants with no `#[serde(tag = …)]` is EXTERNALLY tagged, so it can only ever accept `{"VariantName": {…}}` — never a bare mode string.** `GameCameraMode` was that enum, and `set_game_camera` sent `{ mode: "thirdPersonFollow", followDistance: … }`, so every camera command in the product's history was a hard reject: the AI's camera directive, the inspector, and the GDD pipeline all dispatched into the void. Nothing surfaced it — the store wrote its own optimistic copy, so the UI looked right. The fix is a `from_flat(mode, params)` constructor that reads the flat vocabulary explicitly (PF-1126).
  - **`from_flat`-style constructors make OMISSION the correct way to say "engine default".** Every absent parameter gets the variant's own default, so dropping a field is behaviourally identical to sending the default — but carries no second copy that can drift. Two invented literals in `smartCamera.ts` (`mouseSensitivity: 2` against the engine's 0.1, `autoRotateSpeed: 0` against its 15) were deleted rather than re-pointed for exactly this reason. Note `0` is NOT a neutral omission: it is an explicit "never rotate" that overrides the default.
  - **A hand-mirrored table of engine defaults on the TS side drifts silently and is only checkable by parsing the Rust.** `ENGINE_CAMERA_DEFAULTS` had drifted on two of eight before anything read it, because the panel that displayed those numbers never rendered. The TS suite cannot call `from_flat` and `cargo test` cannot see the TS constant, so `gameCameraPayload.test.ts` reads `engine/src/core/game_camera.rs` textually, fails closed on an unreadable file / missing match arm / unparseable literal, and carries a completeness assertion so a newly added default cannot sit unpinned.
  - **`handle_set_2d_collider_shape` / `handle_set_2d_body_type` did the identical destructive full-replace; fixed by `Physics2dPatch` in PF-1167** — which then found the whole 2D surface disconnected in both directions. Three further outbound breaks sat alongside it: `set_physics_2d` spread its fields FLAT next to `entityId` against an engine that reads a nested `physicsData` (hard reject); `update_physics_2d` and `toggle_physics_2d` were dispatched by the store with no engine arm at any point in their history; and `set_physics_2d` had no way to enable physics, so even a well-formed payload configured a body the simulation never stepped. Two durable constraints came out of the fix. **`Physics2dData` is serialized into `.forge` scenes via `EntitySnapshot`**, so its snake_case field names and PascalCase enum spellings are load-bearing for persistence and cannot be renamed to match a camelCase wire — the patch carries `#[serde(alias)]` (deserialize-only) and the camelCase vocabulary exists solely on the command wire. And **`rename_all` does NOT propagate into a `#[serde(flatten)]`ed struct**, so the emitted event is a camelCase wrapper around snake_case data keys with PascalCase enum values — a mixed casing that looks like a bug and is not.
  - **Two Bevy systems that both `commands.entity(e).insert(T)` on an entity lacking `T` need an EXPLICIT ordering edge; a bare tuple in `add_systems` gives them none, and without one whether the second system sees the component is unspecified — not merely racy.** `.chain()` is what creates the edge, and Bevy inserts an `ApplyDeferred` at every explicit ordering edge, so the first system's insert is FLUSHED before the second runs. `apply_physics2d_toggles` had to be chained before `apply_physics2d_updates` for exactly that reason: the update merges its patch onto the default the toggle inserted, and reversing them applies the default second, resetting the patch. Unchained, the resolution is stable-but-unspecified and flips silently when an unrelated system is added — so repeating a test run will NOT surface it, which is what makes this worth auditing rather than testing. Audit any new pair of apply systems that can insert the same component.
  - **The INBOUND mirror of this class is worse, because a test suite can pin the phantom and pass forever.** A `case 'X'` for an event the engine never emits is silently dead — the switch returns `false` and nothing reports it. `physicsEvents.ts` had arms for `PHYSICS2D_UPDATED`, `JOINT2D_UPDATED` and `PHYSICS2D_REMOVED` (three names nothing has ever emitted), no arm for the `PHYSICS2D_CHANGED` that IS emitted, and a `RAYCAST2D_RESULT` placeholder that returned `true` — claiming a handled event — for another name the engine never sends. Ten tests in `physicsEvents.test.ts` asserted handlers for those phantoms against a wire format that existed only in the suite. **Verify an event name against `engine/src/bridge/events.rs`, never against the suite**, and pin never-emitted names in an `it.each` that asserts the result is `false` AND that no store action was touched, rather than leaving a stub that lies. Two further hazards on the inbound side: an inbound handler must route to a **state-only** store action (`applyPhysics2dFromEngine`), because calling a dispatching action sends a command straight back at the engine — destructively, if that command is a full replace; and an unrecognised enum variant must be dropped, not defaulted.
  - **The same silence exists on the RETURN path, where there is no `dispatchCommand` to blame.** Game components speak THREE vocabularies: the store's nested shape (`{type:'health', health:{…}}`), the command wire (`{componentType, properties}`, snake_case `componentType`), and the engine's flat serde form (`{type:'characterController', …}` — camelCase, from `#[serde(tag="type", rename_all="camelCase")]`). `gameEvents.ts` was CASTING the emitted flat form into the store's nested type, so `comp.characterController` was `undefined` on every component the engine reported and the inspector threw the moment it read a field off it. A cast type-checks and is wrong at runtime — the compile-time analogue of the `satisfies` trap above. The remediation is one translation module owning BOTH directions plus an explicit inverse parser: `web/src/lib/engine/gameComponentWire.ts` (`toWireComponent` / `parseGameComponentWire` / `parseEmittedGameComponent`), the game-component analogue of `lib/game/gameCameraPayload.ts`. Anything unrepresentable is DROPPED and warned once per type, never cast (PF-1141).
  - **Clamp tables mirrored from Rust rot silently, and so do the prose counts describing them.** `ENGINE_PROP_RANGES`/`ENGINE_PROP_MAXIMA` in that module mirror the `prop_f32`/`prop_u32` bounds in `engine/src/core/game_components.rs`; the test parses the Rust textually and carries a COUNT assertion so a newly added call site cannot sit unpinned — same idiom as `gameCameraPayload.test.ts`. A doc comment that states the count in prose ("the engine clamps all eighteen of them") is a second, unpinned copy: pin it too, fail-closed, so a reworded sentence reports rather than quietly pinning nothing.
- **Deserializing, cloning, and DROPPING a `serde_json::Value` are three separate recursions, and on wasm32 overflowing any of them is an unrecoverable trap — not an error.** `serde_json::from_str` caps recursion at 128 levels; `from_value` has NO limit, because by then the `Value` already exists. So a deeply nested command payload overflows the stack, the engine instance dies, and the canvas never draws again for the rest of the session. `core::json_guard` bounds depth (32) and CONTAINER count (50k) without recursing — a recursive checker would overflow at exactly the depth it was written to catch (PF-1149).
  - **Bound the DEPTH, and count only containers — counting every value refuses legitimate bulk data.** The trap is stack frames, so a scalar leaf costs nothing: it adds no nesting to any of the three recursions. The first version of this guard counted every node against 50,000, which silently refused every tilemap past roughly 223×223 — `TilemapLayer.tiles` is a flat array of `width * height` scalars and the inspector permits 1000×1000, so one ordinary edit carries a million values beneath two containers. Counting containers keeps the structural bound meaningful (a 10,000-object waypoint list is still 10,001 containers) while admitting an arbitrarily wide run of scalars. Both suites pin the case: `accepts_a_full_size_tilemap`.
  - **Charge a container against the bound BEFORE pushing it on the scratch stack.** Otherwise a wide array of containers grows the walker's own stack past the bound before the bound is noticed — the iterative checker reintroduces, in heap form, the unbounded growth it exists to prevent.
  - **The guard must take OWNERSHIP of a rejected value and dismantle it iteratively.** `Value`'s derived `Drop` walks its children on the stack, so a guard that borrows returns its error correctly and then aborts the process anyway when the rejected value goes out of scope — i.e. it crashes at the end of the very function that refused the payload. There is no `Result` on `Drop` to catch this.
  - **`dispatch_batch` needs its own check; the per-command one is too late.** Extracting an item's payload does `.cloned()`, and cloning a `Value` recurses exactly like deserializing one. Its bounds are looser by the two levels the envelope itself costs, so a payload legal alone is not refused for being batched.
  - **The Rust guard structurally cannot close the wasm path — only the TypeScript caller can.** `serde_wasm_bindgen::from_value` walks the JS value recursively to BUILD the `Value` before a single line of engine code runs. `web/src/lib/engine/commandPayloadGuard.ts` enforces the same numbers at the last points where the structure is still a JS object. It must descend into `Map` and `Set` as well as arrays and objects: `serde_wasm_bindgen` converts both, and neither exposes its contents as own enumerable properties, so an `Object.values`-only walk reports depth 1 for arbitrarily deep input. The depth bound is also what makes a cyclic payload terminate with a reason instead of hanging the conversion inside WASM — every lap around a cycle re-enters a container, including a branching one, which a depth-first walk descends rather than widens.
  - **The store wrapper is NOT the only path into `handle_command`, and the one it misses is the only genuinely untrusted one.** `useScriptRunner.dispatchCommand` carries payloads built by a user script in the Web Worker, and `structuredClone` posts a value far deeper than `serde_wasm_bindgen` can walk; `useEngine.sendCommand` / `sendCommandBatch` are called directly too. All three are guarded, and `web/src/lib/engine/__tests__/dispatchChokepoints.test.ts` scans every source file that so much as names `handle_command` and fails unless it is allowlisted WITH a reason — deliberately blunt, because a call-site parser needs a comment stripper and a comment stripper is an executable blind region. Adding a fourth dispatch path is therefore a reviewed act, not a silent one.
  - **A batch refusal must be reported ONCE, not once per command.** `reportCommandRejected` dedups Sentry per command NAME for the session, so reporting each entry of a refused batch would both print a line per command and permanently consume every one of those names — a later genuine rejection of any of them would never be reported at all.
  - **`json!({ "k": value })` with a VARIABLE in value position is a recursive re-serialize plus a clone** — it expands to `serde_json::to_value(&value)`. A deep fixture built that way overflows during CONSTRUCTION, which reads exactly like the guard under test failing. Build deep `Value`s by hand (`Value::Object` / `Value::Array` in a loop). Cost two debugging rounds on PF-1149.
- **FOUR independent code paths rebuild an entity from another entity's components, and a component wired into only some of them silently vanishes on the rest.** `spawn_from_snapshot` rebuilds for undo/redo; `insert_aux_components` rebuilds for duplication; `apply_array_requests` and `apply_combine_requests` in `bridge/mesh_ops.rs` build new entities from a source. None errors when it skips a component, so the divergence is invisible from every direction. Shipped live twice, in two different shapes: reverb zones survived an undone delete and were dropped by Ctrl+D (PF-1182); and both `mesh_ops` paths hand-enumerated their carry list (PF-1193) — `apply_array_requests` carried the 3D basics (mesh, material, lights, physics, audio, reverb, particles, shader, CSG, procedural mesh) but dropped 17 of `AuxComponentData`'s 27 fields outright, among them game components, animation clips, the game camera, joints, terrain and every 2D family, so a repeated enemy stopped being an enemy; while `apply_combine_requests` inherited NOTHING from any source — the result spawned with a fresh `MaterialData::default()` and a grey `StandardMaterial` — and pushed source snapshots that omitted physics, lights, the asset ref and every field above, so undoing a combine restored stripped sources.
  - **One list, in `core/`, is the fix — a third hand-maintained list would just add a third thing to drift.** `core/component_carry.rs` owns `AuxComponentData`, `build_aux_index`, `snapshot_entity`, `insert_aux_components`, `insert_base_components` and the `AuxQueries` SystemParam; all four paths call into it. It has to live in `core/` because `bridge/` is `wasm32`-only (`lib.rs` gates `pub mod bridge` behind `#[cfg(target_arch = "wasm32")]`) and so cannot be unit-tested natively at all.
  - **`#[derive(SystemParam)]` is what makes a bridge system able to take the whole carry set.** Bevy caps system parameters at 16, and the old `apply_combine_requests` was already at 14 (array at 10) — which is why an in-file comment had justified cramming reverb into the audio query rather than adding a seventh. The carry set needs seven queries, so unbundled the fixed combine would sit at exactly 16, i.e. at the cap with the next component anywhere breaking it. Bundling them into one `AuxQueries` puts combine at 10 params and array at 5. This is the first `SystemParam` derive in `engine/src`.
  - **A behavioural test for the component you just fixed is nearly worthless here.** It passes forever and says nothing about the NEXT field added. The defect is the divergence, so pin the divergence: `mod component_carry_parity` asserts every field of `AuxComponentData` is collected by `build_aux_index`, written into the snapshot by `snapshot_entity`, restored by `insert_aux_components`, and decided for the combine result by `for_combine_result` — each minus an EXEMPT list carrying a reason per entry. `BaseComponentData` (the non-auxiliary half: visibility, material, light, physics, asset ref) gets the same treatment against THREE writers: `insert_base_components`, its own `for_combine_result`, and the base half of `snapshot_entity`. That third one is easy to miss because `snapshot_entity` takes BOTH bundles and writes them side by side — pinning only the `aux.` half left every `base.` write unpinned, so deleting `snapshot.light_data = base.light_data.cloned();` kept all twenty parity tests green while an undone delete restored an unlit entity. The gate lives in the sibling `core/component_carry_tests.rs`, not inline: it slices the source by marker strings, and a marker written as a literal *inside* the file it scans is a second occurrence of itself.
  - **It compares field NAMES, not semantics — so it cannot catch a field restored WRONGLY, which is how the enablement-marker trap survived the first parity gate.** `insert_aux_components` used to insert `AudioEnabled` unconditionally whenever `audio_data` was present, while reverb's marker was conditional on its own flag; both read their field, so both satisfied the gate, and a muted sound came back playing. `AuxComponentData` now carries `audio_enabled` explicitly (and `EntitySnapshot` gained a `#[serde(default = "default_audio_enabled")]` field so already-serialized `.forge` scenes keep their previous meaning). A field whose enablement is decided differently on different paths still needs eyes.
  - **Combine is N sources → 1 entity, so "carry everything" is not even well-defined — the semantics have to be a written list, not a comment.** `COMBINE_RESULT_EXEMPT` names the 15 fields the result deliberately does NOT inherit from its primary source, with a reason each; the primary source is the first one that actually contributed geometry. Geometry recipes (`csg_mesh_data`, `procedural_mesh_data`) are exempt because the merged mesh IS the result's own; `joint_data` because a joint names entities that no longer exist; `active_game_camera` because a merge must not steal the active-camera flag; the 2D families (`sprite_data`, `physics2d_*`, `tilemap_*`, `skeleton2d_*`) because they describe a 2D entity that a 3D mesh merge does not produce.
  - **The parity gate was SELF-REFERENTIAL until it was pinned against an independent list.** Comparing `AuxComponentData` against code written from `AuxComponentData` proves the two copies agree, not that either is complete. `EntitySnapshot` in `core/history.rs` is the independent list — it is what a `.forge` scene and every undo actually carry — so `the_carry_list_covers_every_snapshot_field_or_says_why_not` diffs its 38 fields against `AuxComponentData` ∪ `BaseComponentData` ∪ a `SNAPSHOT_NON_AUX` list (identity, transform, parent) with a reason each.
  - **`spawn_from_snapshot` is the fourth path and it does NOT go through `insert_aux_components`** — it reads the snapshot directly, so a field `snapshot_entity` writes can be one `spawn_from_snapshot` never reads, and undo restores a stripped entity while returning an `Entity` either way. `mod snapshot_restore_parity` in the sibling `core/entity_factory_parity_tests.rs` pins it: 37 of the 38 snapshot fields must be read, `parent_id` exempt (hierarchy is re-established by the caller's reparent pass, once every entity in the undone batch exists). It REPLACES the older `mod aux_component_parity`, which compared only the duplicate path.
  - Fail-closed like `route_domain_parity`: floors on every parsed count (a slice that quietly returns empty is what makes this class of test report green on a broken parser), a reverse check that every matched name is a real field, and two-direction staleness on each EXEMPT list — an entry that stops being a field fails, and so does one that starts being carried.
  - **Verify by mutation or the gate is theatre.** Reverting the fix must turn the new tests red. Eight mutations were measured on PF-1193, each restored afterwards, and all eight went red: `spawn_from_snapshot` stops restoring skeleton2d; `SNAPSHOT_NON_AUX` loses its `transform` entry; `SNAPSHOT_NON_AUX` gains an entry the carry list already handles; `BASE_INSERT_EXEMPT` loses its `visible` entry; `BaseComponentData::for_combine_result` stops carrying the light; `insert_aux_components` reverts to an unconditional `AudioEnabled`; `insert_base_components` starts inserting `MaterialData`; `snapshot_entity` stops writing `base.light_data` into the undo snapshot. A mutation that fails to COMPILE is not evidence — check the run for `error[` before believing a red. And keep fixtures off-default — `ReverbZoneData::default()` is `preset: "hall"` / `wet_mix: 0.5`, so a fixture built from defaults is satisfied by an `insert(default())` mutant that restores nothing real.
- **A Rapier collider exists ONLY on an entity carrying `PhysicsEnabled`, so an entity the pipeline spawns and never enables is scenery — and every downstream gameplay system reads as broken instead.** `manage_physics_lifecycle` (engine/src/core/physics.rs) attaches the collider `With<PhysicsEnabled>`; `system_track_collisions` builds `runtime.active_collisions` purely from the `CollisionEvent`s those colliders emit; `system_collectible`, contact damage and `system_win_condition`'s score path all read that set. The game-creation pipeline spawned the player, the world geometry and the collectibles and never once dispatched `toggle_physics`, so `active_collisions` was empty in every generated game: the player fell through the ground, no pickup fired, score never moved and `game_win` was unreachable.   - **The player must be `dynamic`, and this is not a style choice.** Rapier's default `ActiveCollisionTypes` is `DYNAMIC_DYNAMIC | DYNAMIC_KINEMATIC | DYNAMIC_FIXED` and the engine never inserts a widened set, so a KINEMATIC player against FIXED ground or a FIXED collectible produces NO events at all. The game looks correct and is unwinnable. Every pair the pipeline creates therefore has a dynamic side; the table is `lib/game-creation/physicsRoles.ts`.
  - **A pickup must be a sensor.** `manage_physics_lifecycle` inserts Rapier's `Sensor` when `is_sensor` and `ActiveEvents::COLLISION_EVENTS` regardless, so a sensor pair still reaches `active_collisions` while a solid collectible would be punted across the level on contact.
  - **`toggle_physics` and its `update_physics` patch cannot ride the same frame.** `apply_physics_updates` is registered BEFORE `apply_physics_toggles` in `bridge/mod.rs` and the 3D pair is deliberately NOT `.chain()`ed, so Bevy inserts no `ApplyDeferred` between them: the update runs first, finds no `PhysicsData`, `tracing::warn!`s and DROPS the patch. Omitting a field from the patch is the correct way to say "engine default" — `toggle_physics` inserts `PhysicsData::default()`, so a mirrored copy of every number would only give it something to drift against.
