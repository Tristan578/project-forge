# Gotchas — Claude Code Config, Infrastructure & Hooks

## Claude Code Config
- **`.claude/prompts/` ≠ `.claude/skills/`** — Prompts are template files only accessible from the prompt bar UI. Skills (in `.claude/skills/<name>/SKILL.md`) are invocable via `/name` from the CLI and via the `Skill` tool. If it should be callable as `/foo`, it MUST be a skill, not a prompt. Never create automation in `.claude/prompts/`.
- **Hook input: two patterns, not interchangeable** — Edit/Write hooks get `TOOL_INPUT_<field>` env vars (e.g. `TOOL_INPUT_file_path`). Bash hooks get stdin JSON parsed with `jq -r '.tool_input.command'`. Using the wrong pattern = silent no-op. For Bash hooks, source `.claude/hooks/hook-utils.sh` and call `get_bash_command()`. See `check-pr-metadata.sh` for the canonical Bash hook pattern.

## Infrastructure
- **WASM CDN fallback — same-origin requires JS glue + WASM from same origin** — `useEngine.ts` tries CDN first, falls back to `/engine-pkg-*/`. Both JS glue and WASM binary must come from the same origin (CDN or same-origin) due to wasm-bindgen import path coupling. To force same-origin: unset `NEXT_PUBLIC_ENGINE_CDN_URL`. AbortError from navigation is suppressed in the `useEngine` `.catch` handler (not inside `loadWasm` itself) so it doesn't surface as a user-visible error.
- **Vercel account scope** — ALWAYS use `--scope tnolan`. Never `nolantj-livecoms-projects`.
- **Worktree branch loss** — Nested worktrees lose branches. Never nest. Always rebase onto main first.
- **Schema changes need migrations** — `db:push` works in dev but production needs `ALTER TABLE`.
- **IV/crypto changes need migration path** — Changing parameters breaks existing stored data.
- **`experimental.sri` is incompatible with Vercel CDN** — Do NOT re-enable.
- **Stripe v22 API version** — On `22.4.0`, API version `2026-07-29.dahlia` (the SDK pins its `ApiVersion` literal; `apiVersion` in `stripe-client.ts` MUST match the installed SDK or tsc fails). No `decimal_string` fields used — all amounts are integer cents. When bumping `stripe`, update the literal in `stripe-client.ts` + the 3 billing route tests (status/portal/checkout) + the webhook `route.ts` comment.
- **Max 5-7 fixes per builder dispatch** — Agents rushing through 25+ lists introduce anti-patterns.
- **GraphQL rate limit exhaustion** — Use `gh issue list` (REST) for sync, not `gh project item-list` (GraphQL).
- **A Projects v2 item id is NOT an issue number, and a stand-in for one is a billed request that can never succeed.** `pull()` fetches issues over REST, which does not know the board item they belong to, so it normalized them into board-item shape with `id = f"issue-{number}"`. `push()` then fed that stand-in to `gh project item-edit --id`, which can only answer `Could not resolve to a node with the global id of 'issue-N'`. The raise aborted the ticket's update block BEFORE `lastLocalStatus`/`bodyHash`/`metadataVersion` were written, so the change detector fired again on the next run — 922 tickets replayed once per Stop hook, forever (PF-1212 / #9340). Only `PVTI_`-prefixed ids reach a mutation now (`is_real_project_item_id()`, enforced inside `gh_set_status` so no call site can route around it); anything else is resolved on demand via a single-issue GraphQL query or skipped. Board Status is a MIRROR — its failure is counted, never raised, or the latch comes straight back.
- **Sync kill switch: `touch .claude/hooks/.sync-disabled`** (or `export SPAWNFORGE_SYNC_DISABLED=1`). Honoured by `sync-to-github.sh`, `sync-from-github.sh`, and `github_project_sync.py` itself, before any of them probe `gh`/`curl`. The Stop hook fires the push after EVERY assistant response, so there is no interactive moment in which to stop a misbehaving sync — the previous lever was holding its `fcntl.flock` from a detached process and remembering to kill the pid. `rm` the marker to re-enable.
- **The detached reconcile sweep and the Stop-hook push share one exclusive lock.** The sweep lists every issue in the repo, so every second it holds the lock is a push that skipped. A run that cannot take the lock writes `.sync-lock-wanted`; the sweep checks it between items and stops early (it is state-based and idempotent, so the remainder is simply recomputed next time). Both sides are also wall-clock bounded — `SPAWNFORGE_SYNC_PUSH_BUDGET` (120s) and `SPAWNFORGE_SYNC_RECONCILE_BUDGET` (300s).
- **Taskboard `localProjectId` drifts** — Verify sync config against `curl http://localhost:3010/api/projects`.
- **Under Rolling Releases the public domain serves TWO builds, and the deployment URL is SSO-protected — verify the CANARY, through the public domain, by commit.** `vercel deploy --prod` returns a `*.vercel.app` URL behind Vercel Authentication that CI cannot fetch (the old health check `vercel curl`'d it, could never authenticate, and warned-and-exited-0 on every production run), while `www.spawnforge.ai` is 95% the PREVIOUS build for the first 10 minutes of a rollout (so the smoke suite graded yesterday's deploy). `?vcrrForceCanary=true` on the public domain answers with the `_vcrr_*` cookie that pins a client to the canary; carry it in a cookie jar / browser context and assert `/api/health`'s `commit` equals `github.sha` — that is the only proof the probe reached THIS deploy. The cookie lives only as long as that one rollout, so a missing cookie is a warning and the commit assertion is the gate. (#9624)
- **A deploy that lands while an older rollout is still ramping is silently never rolled out** ("the project's state won't change" — vercel.com/docs/rolling-releases); main @ 8aee29f9 shipped that way on 2026-09-02 and never served a byte. `scripts/cd-rolling-release.sh ensure-canary` aborts a stale OLDER canary (Instant Rollback to its base) and starts ours via `POST …/rolling-release/start` before anything is verified; a NEWER canary means the run is superseded and it refuses to touch the rollout. A canary whose `createdAt` cannot be read is refused too — older-or-newer is the whole decision. (#9625)
- **`vercel promote` is not a rollback under Rolling Releases.** A promote of an old build either STARTS a staged rollout of it or, while a rollout is active, is a silent no-op — neither reverts traffic. Every rollback path (automatic, manual dispatch, runbooks) must be `vercel rollback` / `POST /v1/projects/{id}/rollback/{dpl}` (Instant Rollback). (#9624)
- **Instant Rollback turns auto-assignment of production domains OFF** until a rolling release completes (vercel.com/docs/instant-rollback#undo-a-rollback): after any rollback — CD's automatic one, a manual one, or `ensure-canary`'s abort of a stale canary — pushes to `main` no longer go live by themselves. `ensure-canary` starts the next rollout explicitly, and a refused start after an abort is a hard error naming the base now serving (`mutated=true` in `GITHUB_OUTPUT` lets cd.yml roll back and open the incident); the undo by hand is `vercel promote <fixed-url>`. Every runbook that says "roll back" must also say this. (#9624)
- **cd.yml serialises production deploys; never re-enable `cancel-in-progress` on its concurrency group.** A run cancelled after `vercel deploy --prod` leaves its unverified canary ramping (auto-assign starts the rollout on READY; the stage schedule auto-advances it to 100% in ~10 minutes) with every `failure()`-gated step skipped — `cancelled()` is not `failure()` — so nothing rolls it back or records it, and the next run's `lkg` captures that unverified build as last-known-good. A human cancellation after the deploy opens a P0 issue telling the operator what to check; it does not mutate production. (#9624)
- **A probe that fails because a later deployment took over is not an unhealthy build.** Merges are serialised, but an out-of-band deploy (manual `vercel deploy --prod`, a `promote_to_production` dispatch on another ref) is not: its `ensure-canary` aborts this run's still-ramping rollout by design, the forced cookie is re-randomised, and the commit assertion trips on the base or on the newer canary. Rolling back THEN would Instant-Rollback production to the older base and abort the newer, healthy rollout, whose probe then fails and rolls back too. cd.yml therefore runs `cd-rolling-release.sh superseded` before any rollback and skips the rollback and the incident issue when a NEWER deployment owns production (`superseded=true`, `owner=<id>`); a lookup that cannot answer says `false`, so an unexplained failure is still rolled back. When no rollout is active the owner is the project's production target — the same source `lkg` uses — never the idle rolling-release record, which is history. (#9624)
- **`ensure-canary` reports a `disposition` so cd.yml knows whether a failed canary step may have left the build live.** `untouched` (a foreign canary is active, ours is at most queued) is the only failure that skips the rollback; `started` (our start was accepted, then a lookup failed), `mutated` (abort issued) and `unknown` (transport error before anything was known — auto-assign may already have started the rollout) all roll back to the pre-deploy `prev_url` and open the incident. (#9624)
- **The rolling-release GET wraps its document, and `vercel ls | grep READY` never matched.** Read `.rollingRelease.state` etc. and treat `"rollingRelease": null` as "no rollout" — the CLI's `rolling-release fetch` destructures the wrapper before printing, which is how a first cut read the fields at the top level and passed a suite whose fixtures made the same mistake (the suite now carries a live document verbatim). `vercel ls` prints `● Ready`, so the grep-based last-known-good capture was empty on every run and automatic rollback had never fired; `cd-rolling-release.sh lkg` reads `rolling-release.currentDeployment` (the base, never the newest READY row, which is the canary). (#9624)

## Enforcement Hooks
- **`block-deferred-fixes.sh` fails closed** — If body extraction fails, the hook BLOCKS (exit 2), not allows (exit 0). Previous behavior silently let unparseable replies through.
- **Subagent hook inheritance gap** — `.claude/settings.json` PreToolUse hooks do NOT fire for subagents. The `block-deferred-fixes.sh` hook only catches the main agent. Subagents must self-enforce via the banned-phrase list embedded in `/resolve-pr-comments` SKILL.md.
- **Bare SHA is not enough** — A reply must contain BOTH a commit SHA AND an action verb ("Fixed in", "Addressed in"). A reply like "Good catch abc1234" is blocked — it has a SHA but no action verb, so it's likely deferred-fix language with an unrelated hex string.
- **`#NNNN` ticket reference is acceptable** — A deferred reply with a real GitHub issue number (#8307) is allowed. The rule is "fix it or track it", not "fix it or die".
- **Two hooks can each be correct and jointly unsatisfiable — check the OTHER hooks on the same tool before adding a constraint.** `block-main-commits.sh` refuses to analyse a Bash command over 4000 chars and directs large content to a file; `check-pr-metadata.sh` used to grep only the COMMAND STRING for `Closes #NNNN`, and its own comment admitted it "catches inline `--body` but not `--body-file`". Together they made any substantive PR body unsubmittable: inline was too long to allow, and `--body-file` could never satisfy the `Closes` check. Both hooks passed their own tests; nothing tested the pair. It shipped and blocked the PF-1051 PR (PF-1052). Fixed by teaching `check-pr-metadata.sh` to extract the path from `--body-file <path>` / `--body-file=<path>` / `-F <path>` (quoted or not) and read THAT file.
  - **When a body file is present it is the only thing gh sends, so it alone decides** — a `Closes #NNNN` sitting elsewhere in the command (in `--title`, say) must not launder a linkless body file. Fails closed on a missing/unreadable/directory path or a flag with no value: an unverifiable body is not a verified one.
  - **A blocking hook MUST write its reason to STDERR — the harness surfaces stderr on exit 2, so a reason echoed to stdout arrives as "No stderr output" and the block reads as a mystery instead of a policy.** `check-pr-metadata.sh` printed a full diagnostic to stdout and was silent from the caller's side for its whole life. Wrap the message block in `{ ... } >&2` — the convention `block-main-commits.sh` already documents. Pinned by a `check_err` assertion per blocking path.
  - **A `--title` that MENTIONS a flag is indistinguishable from the flag itself to a grep-based hook.** These hooks cannot parse shell quoting, so first-occurrence extraction pulled the path `so` out of the title `read --body-file so the PR metadata check is satisfiable` — this hook's own PR title — and blocked on it. Scan EVERY occurrence and take the first that names a readable file, falling back to the first occurrence so a command with no usable path still fails closed.
  - **Piping a variable into `grep -q` is SIGPIPE-unsafe under `set -o pipefail`** — `grep -q` exits on first match, SIGPIPEs the writer, and the pipeline reports failure, INVERTING the verdict of a negated test. Use a here-string instead. Latent while commands stay under the pipe buffer; free to remove. `.claude/hooks/__tests__/check-pr-metadata.test.sh` carries a structural guard against reintroducing the pattern.
- **60+ deferred-fix phrases** — The hook checks for phrases like "known limitation", "out of scope", "low-priority", "acceptable tradeoff", "future refactor" in addition to the obvious "will fix later" family. Full list in `.claude/hooks/block-deferred-fixes.sh`.
