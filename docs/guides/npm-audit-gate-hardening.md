# npm-audit gate — self-defense hardening log

`scripts/check-npm-audit.sh` is the allowlist-based `npm audit` gate; its
decision logic is unit-tested by `scripts/__tests__/check-npm-audit.test.sh` in
the `lockfile-sync-tests` ("CI Self-Defense Tests") job. Beyond testing the
gate's own branches, that suite pins the CI wiring that makes a red audit
actually BLOCK — because a gate that can be unwired by one line is not a gate.

This file is the log of how those pins were arrived at: each round attacked the
previous round's pins, measured what stayed green, and closed what it found. It
is kept out of `.claude/rules/gotchas.md` (which is loaded into every session)
because it is reference material for whoever next edits the gate, the suite, or
the workflows they pin — not a gotcha to carry around.

Read this before weakening, widening or removing any assertion in that suite:
most of them exist because a plausible-looking alternative was measured and
found to pass on a live neuter. The recurring shape, stated once here and
re-derived the hard way a dozen times below, is that **a pin constrains exactly
what it names** — a key set says nothing about values, a value pin says nothing
about continuations, a pin on one variable says nothing about the variable one
assignment downstream, and a check whose evidence is produced by the thing it
audits cannot fail when that thing is removed.

Every claim below was measured against a clean replica with a green control.
None of it is airtight: a coordinated edit of both a workflow and this suite
defeats any of these pins, so human review of any `ci.yml` / `cd.yml` /
`quality-gates.yml` / `scripts/` change remains the backstop. What the
automation closes is the silent single-line slip.

## What the suite pins inside the gating jobs

The suite also pins the wiring that makes a red audit actually BLOCK: no step-level `if:`/`continue-on-error:` on any audit step, no job-level `if:`/`continue-on-error:` on the quality-gates security job, and no job-level `continue-on-error:` on cd.yml's security job — cd.yml's security job legitimately carries exactly ONE job-level `if:` (main-push/workflow_dispatch only), which the suite pins to that count and to containing `refs/heads/main` rather than pinning it absent (for why every YAML-key assertion matches its key through a quote class, and the exact-line-set idiom that grew out of it, see [Aside: key spellings, and the exact-line-set idiom they forced](#aside-key-spellings-and-the-exact-line-set-idiom-they-forced)), no job-level `needs:` on EITHER security job (on quality-gates a conditional dependency like `editor-boot` would cascade-skip it and a skipped required check reads as satisfied; on cd.yml a skippable dependency like `build-wasm` — which skips on any non-engine push — would cascade-skip the audit into a deploy-through, since that job's `if:` has no `always()` to rescue it), `security` stays a flow-list element of the `needs:` lists of cd.yml's `deploy-staging` and `deploy-production`, AND each of those deploy jobs' `if:` bodies still contains the explicit `needs.security.result == 'success'` clause (deploy-staging directly, deploy-production in its `workflow_dispatch` promote branch).

The clause pin is the load-bearing half of that edge: both deploy `if:` blocks start `always() &&`, under which a FAILED dependency does not skip the dependent job — so `needs:` membership alone blocks nothing (it only makes `needs.security` resolvable), and deleting the one clause line leaves the workflow valid while a red audit no longer stops either deploy. The clause pin matches inside the cut job-level `if:` block ONLY — a needle occurrence elsewhere in the job (an `env:` value, a step name) has no gating effect and does not satisfy it — each deploy job's `if:` key is also count-pinned to exactly one (YAML keeps the last duplicate key, so an appended second `if: always()` would override the clause at runtime while the intact original block still satisfied containment) — and it proves the clause is PRESENT, not that it is EFFECTIVE: a vacuous rewrite like `(needs.security.result == 'success' || true)` still passes, since resisting that would mean parsing GitHub Actions expressions (same raises-cost-not-airtight register as the other anti-tamper checks here).

The skipped direction is covered too: `deploy-staging`'s `if:` accepts `needs.security.result == 'skipped'`, and `deploy-production` inherits that exposure on the push path (its push branch gates only on `needs.deploy-staging.result == 'success'`, never on `security` directly) — so a SKIPPED security job would satisfy both deploy gates, and the if:-count/containment and needs:-absence pins above, which keep the security job itself un-skippable, are load-bearing for the same guarantee. (`deploy-docs`/`deploy-design` are NOT audit-gated at all — pre-existing gap, tracked in PF-1011/#9030.) Both security jobs' job-level `steps:` key is count-pinned to exactly one — the severe member of the duplicate-key class: an appended second `steps:` at the end of the job replaces the ENTIRE step list under YAML last-key-wins (all three npm audits + cargo audit gone) while the job exits 0 and reports SUCCESS, not skipped, so the `CI Success` skip-based anti-tamper never fires; on cd.yml a replaced step list additionally makes `needs.security.result == 'success'` genuinely TRUE, satisfying every deploy clause pin on its own terms.

The step-scoped textual assertions can't tell which `steps:` key owns the steps they match — with exactly one, the scanned steps ARE the effective steps.

## Aside: key spellings, and the exact-line-set idiom they forced

(every YAML-key assertion in the suite — count, absence, and containment alike — matches its key through a `["']?` class, because YAML accepts a key in EITHER quote style — `"if":` and `'if':` are the same key as `if:`, and a double-quote-only class left single-quoted duplicates of every pinned key green. The same spelling class bites a SECOND construct that is easy to miss when sweeping the matchers: the awk **terminators** of the job-block cuts. A bare-only terminator (`^  [A-Za-z_][A-Za-z0-9_-]*:`) does not stop at `  'zz-decoy':`, so for a job that is LAST in the file — `ci-success` is — the cut runs to EOF and every pin beneath it reads a FOLLOWING job's keys. That is worse than a false positive: deleting ci-success's `needs:` and appending a single-quoted decoy job carrying `- quality-gates` produced a GREEN suite plus the affirmative line "ci-success still lists quality-gates in its needs: aggregate" while ci-success listed nothing (the bare-key form of the same mutation was already caught, so the quote was the entire ingredient).

All six job-level cuts now share one quote-tolerant, colon-REQUIRING terminator (`^  ["']?[A-Za-z_][A-Za-z0-9_-]*["']?[[:space:]]*:`). An intermediate round dropped the colon on the theory that inside `jobs:`, any 2-space letter-initial line IS a job key since properties sit at 4 spaces — that theory is FALSE and dropping it was a regression two review seats caught independently. YAML indentation bounds BLOCK structure, not scalars: a multi-line quoted scalar continues at ANY indentation, including less than its own key's, so `name: "trunc` / `  decoy"` puts a 2-space colonless line INSIDE the job. The colonless class matched it and TRUNCATED the cut, and every pin below then read a block missing the keys it pinned — which fails OPEN, because count pins ("exactly one `steps:`") and absence pins ("no `continue-on-error:`") are satisfied by evidence that was cut away. Strictly worse than the quoted-decoy finding above, which at least turned the required check red: here the appended duplicate `steps:` wins under last-key-wins, every audit is replaced by an echo, and the job still reports SUCCESS.

The key-level cuts elsewhere stay colonless SAFELY, and that asymmetry is why the precedent didn't transfer: they host positive containment pins, where truncation removes the NEEDLE and fails closed; only job-level cuts host count/absence pins. Because a continuation can also carry a colon (`  B: 2}`) or be spelled exactly like a bare job key (`  decoy:`), the charset alone is insufficient at any width. An intermediate round tried to close that with two SHAPE-based preconditions — every 2-space line inside `jobs:` looks like a job key, and no line opens an unclosed quoted scalar or flow collection — and both review seats breached the second one within the same round, independently and with different payloads: a backslash-escaped quote (`concurrency: "grp\"`) survives an even-parity quote count while leaving the scalar open, and an opener that isn't shaped `key: value` — a bare sequence item (`- "a`), an anchor (`&a "trunc`), a tag (`!!str "trunc`) — is never examined at all.

Each was measured live: suite green, PyYAML confirming a job with `continue-on-error: true` and its whole step list replaced. The lesson is that "does this line LOOK like a job key?" is a blacklist against unbounded YAML spellings, and three successive widenings each traded one spelling for the next. So the suite instead pins the EXACT SET of 2-space lines inside `jobs:` per workflow (11 / 14 / 22 job keys), which is spelling-independent by construction: a continuation, however opened or spelled, is a 2-space line absent from the list. It also covers the reverse direction no shape test did — respelling a REAL job key (`  "security":`) so the terminator stops matching it and the PRECEDING job's cut over-runs into it. It fails closed in every direction (a missed section anchor, an early-ended section, or a grown workflow all yield a mismatch, and an empty enumeration is refused outright rather than passing vacuously — the same discipline `check-openapi-route-sync.sh` applies to an empty route enumeration), and the section anchor is quote-tolerant to match the sibling top-level `jobs:` count pin.

That enumeration then turned out to carry the SAME defect one level up, found independently by two review seats with different payloads: the exact set was pinned, but the scan's own BOUNDARY was still inferred line by line (`awk` started at `jobs:` and stopped at the next column-0 line). A quoted scalar continues at ANY indentation INCLUDING column 0 while staying inside a nested job, so the section could be ended from inside a job body and every job key after that point simply never enumerated. At most cut sites that costs the attacker the FOLLOWING job keys and turns the suite red; in the LAST job of a file every key has already printed and the kill is FREE. `ci-success` is last in ci.yml, is a cut target, and hosts a count pin (exactly one `needs:`) that fails OPEN when its block is truncated — measured live at 146/0 green while PyYAML resolved `ci-success.needs == ['ci-gate']` with the `- quality-gates` aggregate gone.

Fixed by applying the same discipline to the boundary instead of widening the rule again: the scan now runs to EOF (no boundary rule is load-bearing at all), and the exact ORDERED set of column-0 keys is pinned per workflow (5 / 6 / 5), which inherently pins `jobs` as the LAST top-level key — the premise scanning to EOF rests on. Values are stripped (`name: CI` → `name`) so a cosmetic workflow rename stays green; no column-0 value is load-bearing. A continuation spelled exactly like a real top-level key still lands as an extra ordered element, so the comparison catches it. Cost, by design: adding, renaming or removing a job turns the suite red until the list is updated — a one-line, obviously-correct edit, and for a self-defense suite the prompt is the point. Scope, honestly: this makes the cuts' premise VERIFIED rather than assumed for these three files; it does not make line-based cutting sound in general, and like every pin here a coordinated edit of both the workflow and the suite defeats it, so it raises the cost of textual tampering without claiming to be airtight.

Two later rounds extended the same discipline in both directions. First the enumeration's own false-POSITIVE direction: an exact-set comparison mismatches on ANY cosmetic difference, so a trailing comment or trailing whitespace on a genuine job-key line (`  security:  # gate`) reddened the suite over nothing. Both are stripped before comparing — the opposite polarity from the containment assertions below, where a needle alive only inside a comment is tampering; here a comment is noise. Then the RESIDUAL this note used to record — that the pin governed the 2-space JOB-key lines only, while keys INSIDE a job were still matched by bytes through the `["']?` class — turned out to be a LIVE hole, not a theoretical one, and was closed by applying the enumeration one level deeper. YAML 1.2 resolves `\u` escapes inside double-quoted scalars, so `"\u0073teps"` and `steps` are the SAME mapping key to the parser and different byte strings to grep.

Appending `"\u0073teps":` plus one `- run: echo pwned` to quality-gates.yml's security job measured 150 PASS / 0 FAIL while PyYAML resolved that job to `steps=1` with ZERO audit steps — all three npm audits and the cargo audit replaced, the job reporting SUCCESS rather than skipped, so the skip-based anti-tamper never fires either. The plain spelling of the identical payload is RED, which is what makes the escape the whole ingredient; an escaped `continue-on-error` and an escaped `needs:` were false green the same way. Fixed by pinning the exact set of 4-space keys in every cut job block, values stripped as at column 0 — no job-level VALUE is load-bearing for THIS pin, and the ones that are load-bearing elsewhere — five of them, not the three an earlier draft of this note listed: the deploy `if:` clause, the audit `run:` lines, the caller's `uses:`, the security job's `name:` (what the branch-protection rule matches on), and ci-success's own job-level `if:` (`always()`, without which the required check SKIPS, and a skipped required check reads as satisfied) — keep their own containment assertions, so a cosmetic job rename stays green.

A 4-space continuation from a multi-line scalar carries no colon, survives the strip intact, and lands as an unexpected element; an emptied block is refused outright rather than passing vacuously. All six cut blocks carry it, and the last one earned its place by measurement rather than reasoning: the ci.yml `quality-gates` caller looked like uniformity-only, on the theory that its `uses:` pin is positive containment and so fails closed. It does NOT — an appended escaped `"\u0075ses": ./.github/workflows/decoy.yml` repoints the reusable-workflow call under last-key-wins while the ORIGINAL `uses:` line still satisfies containment, measured green pre-fix with the sole execution site of all three npm audits pointed at a decoy. Scope, as everywhere here: spelling-independent, NOT parser-equivalent — whether GitHub's own workflow parser resolves `\u` escapes the way PyYAML does is not something this suite measures)

## The gate must still be INVOKED

Orthogonal to every pin above — which all cover the INSIDE of the gating job — the suite also pins that the workflow CONTAINING it is still INVOKED: `quality-gates.yml` is `workflow_call`-only and is called from exactly one place, ci.yml's `quality-gates:` job, and since cd.yml does not run on `pull_request` at all, that caller is the SOLE execution site for all three npm audits on the PR path. So the caller's JOB key is count-pinned to one, its `uses:` is pinned to `./.github/workflows/quality-gates.yml` (repointing it leaves quality-gates.yml on disk with every pin intact and auditing nothing), and its `if:` is count-pinned to one whose comment-stripped body still contains `needs-any-code` — an `if: false` there leaves the job EXISTING, so ci-success's `needs:` list still resolves and the job merely SKIPS, which `check-ci-success.sh` USED to certify green (it fails only on failure/cancelled).

PF-1010 closes that skip direction externally by adding `check_triggered "quality-gates" "needs-any-code"` to that verifier's anti-tamper map — one-armed by construction, since `needs-any-code` is the caller's sole `if:` trigger, so a docs-only PR leaves it unfired rather than false-positive. That entry is load-bearing only while the TRIGGER ITSELF is honest, which is the residual round 27 closed — and the residual is exactly the shape this whole entry keeps re-learning, one level further out: `needs-any-code` is not a fact, it is a VALUE computed by an unpinned shell block inside `ci-gate`'s "Detect changed paths" step, and `ci-gate` was not one of the four jobs whose `steps:` lists round 24 pinned. Flipping the single token `any_code=true` → `any_code=false` there measures **181 PASS / 0 FAIL**, identical to control: the caller's `if:` becomes unsatisfiable on EVERY PR, so the sole PR-path execution site of all three npm audits never runs, and `check-ci-success.sh` still exits **0** printing "All required gates passed (or were correctly skipped via path filter)".

`check_triggered()` fails closed on a REMOVED or RENAMED output but has no arm for a FALSIFIED one — a false trigger is indistinguishable from a legitimate path-filter skip, which case 56 of `check-ci-success.test.sh` deliberately asserts must pass. The stealthier spelling — deleting the `|| [ "$ci" = "true" ]` arm from the condition — measures the same and disarms only on workflow/scripts-only PRs, i.e. precisely the PRs that would carry the tamper; and since `pull_request` runs the PR's own workflow file, either mutation takes effect in the very run that should catch it. Fixed by the sixth application of the exact-line-set idiom: `ci-gate`'s job key is count-pinned, its 4-space key set enumerated (which is what closes a job-level `if:` and a `continue-on-error:` on the detect step), and its `steps:` list pinned verbatim at 52 comment-stripped lines. Its `outputs:` mapping is pinned verbatim SEPARATELY, because those entries sit at SIX spaces — below the four-space enumeration — so `needs-any-code: 'false'` would otherwise be a green one-line unwire, the same depth-of-nesting gap that recurred at column-0, 2-space, 4-space, step-key and step-line level before it.

Eight vectors red-verified against a clean replica with a green control: the value flip, the deleted `||` arm, a rewritten `echo "any-code=false"`, a later `any_code=false` appended BETWEEN the condition and the emit block (which defeats a containment pin on the condition alone — hence a line SET over the whole step), both `outputs:` spellings (repoint and duplicate key), the step `continue-on-error:`, and a job-level `if: false`. Churn cost is ~zero by construction: the suite already pins ci.yml's exact job-key list, so adding a new CI gate already reddens it and the detect step is edited in the same commit. The same entry closes a SECOND one-line unwire, the cheaper one, which no pin covered and which the note previously here got WRONG: deleting `- quality-gates` from ci-success's own `needs:` block list is valid YAML with no dangling reference — the caller still runs, the required aggregate just stops observing it, so a red audit leaves "CI Success" green. (The old claim — "deleting the caller job outright needs no pin: ci-success still lists it in `needs:`, a workflow validation error" — was false reasoning that reached a true conclusion by luck; caller deletion is caught by the caller job-key count pin, and an absent job is flagged by the verifier ONLY for jobs its map lists. The suite now also pins ci-success's job-key count, its single `needs:` key, and `- quality-gates`'s membership in that list.) `ci-success` additionally carries the job-level `steps:` count pin the three audit-bearing jobs already had, plus a containment pin that its single `run:` scalar still invokes `check-ci-success.sh` (a replaced-but-single `steps:` list is the next spelling after the duplicate-key one).

It was the ONLY block-cut job without that pin, and it is the job that RUNS the verifier every other pin here leans on for runtime enforcement: three appended lines replace its step list under last-key-wins, and because its `if: ${{ always() }}` keeps it running when quality-gates fails, it would execute an echo and report SUCCESS — the required check green over a red audit, with no skip for the skip-based anti-tamper to notice. The suite's OWN CI execution is pinned the same way: the `lockfile-sync-tests` job's suite-run step (`Run npm-audit allowlist gate test suite`) and shellcheck step are each cut via `step_block` and carry the full triple — no step-level `if:`, no `continue-on-error`, exactly ONE `run:` key (an appended `run: true` executes INSTEAD of the suite under last-key-wins, and for `pull_request` events GitHub runs the PR's workflow file, so the mutation takes effect in the very run that should catch it — the one pin whose failure makes every other green prove nothing) — plus containment: the suite-run step's single `run:` line is whole-line-anchored to `bash scripts/__tests__/check-npm-audit.test.sh`, and the shellcheck needle (gate + suite paths) is scoped to the `run:` SCALAR cut, not the step block, so an `env:`-value smuggle inside the same step can't satisfy it (this proves the needle sits in the executable scalar, NOT that shellcheck semantically lints it — same present-not-effective residual as the deploy clause pin).

The auditing job itself (`lockfile-sync-tests`) carries the same job-level pins it enforces on its targets — exactly one job-level `steps:` key and no job-level `continue-on-error:` (either neuter leaves the job reporting SUCCESS, not skipped, so the skip-based anti-tamper never fires); its legitimate job-level `if:` (the ci-gate trigger) is deliberately NOT count-pinned, since an appended `if: false` SKIPS the job — which the `CI Success` verifier genuinely catches — and an appended `if: true` only widens when the job runs.

## Duplicate-key hierarchy: job keys, and the `jobs:` key itself

Topping out the duplicate-key hierarchy, all five load-bearing JOB keys — every job the suite block-cuts: `security` in quality-gates.yml and cd.yml, `deploy-staging`/`deploy-production` in cd.yml, `lockfile-sync-tests` in ci.yml — are count-pinned to exactly one definition: every job-block cut anchors on the FIRST `^  <job>:` match, so an appended duplicate job at end of file would replace the whole job under last-key-wins (display name preserved, job reports SUCCESS) while every pin read the dead first block — on cd.yml additionally making `needs.security.result == 'success'` genuinely TRUE for a replaced security job, and a replaced DEPLOY job simply deploys with no `needs:` and no gating clause at all (cd.yml runs on push to main, so no required-check absence backstops it). The level above the job keys — the top-level `jobs:` key itself — is count-pinned in all three workflows too: an appended second `jobs:` mapping replaces EVERY job under last-key-wins while all job-key pins read the dead first mapping, and an earlier "fails closed on its own (it collapses every job)" self-defeat argument was tested and rejected — the collapse is real, but what survives it is the attacker's choice (a replacement re-declaring only ungated deploy jobs left the suite green pre-pin), not a fail-closed property of YAML. (Duplicate-key mutations of every flavor above would be flagged by actionlint, but actionlint is not wired into this repo's CI; last-key-wins is verified against a real YAML parser plus the documented duplicate-`env:` precedent above, not against GitHub's own workflow parser.)

## Comment stripping has two opposite polarities

Every containment-style positive assertion runs on a trailing-comment-stripped copy of its line — the strip does NOT require whitespace before the `#`, because in YAML flow context `]#` still opens a comment — since a needle alive only inside a YAML trailing comment (`needs: [...] # [security]`, `needs: [...]# [security]`, `if: false # refs/heads/main`) is tampering, not wiring.

## Exact line sets, level by level

The exact-set enumeration then went one layer deeper AGAIN, for the same reason and with the same result — assume this pattern recurs at any level a pin matches key names by bytes. Every STEP-scoped pin (the `if:`/`continue-on-error:` absence checks, the `run:` count, the whole-line containment) still matched through the `["']?` class, so the escape class closed at job level was live one level below it, inside the very steps this gate's payload runs in. Appending `"\u0072un": echo pwned` to ci.yml's ci-success verify step measured 160 PASS / 0 FAIL while PyYAML resolved that step's effective `run:` to the echo — the required check's OWN verifier replaced, job still reporting SUCCESS. Escaped `if` and escaped `continue-on-error` were false green the same way, at all NINE cut step sites (the six audit steps — three per security job, not two — plus ci-success's verifier and the suite's own two CI steps; an earlier revision of this sentence said "seven" with a parenthetical summing to eight, and dropped ci-success's verifier, the most security-relevant of the nine since it runs the sole required check's verifier and was the very step the preceding sentence's own payload targeted).

Fixed by `assert_step_level_keys`, the fourth application of the idiom after column-0, 2-space and 4-space: the exact set of `      - name`-style and 8-space key lines per cut step, values stripped. Four PLAIN step-level payloads on ci-success were red-verified alongside it, each previously green at 150 PASS / 0 FAIL and PyYAML-confirmed live — a duplicate `run:` (last-key-wins, original line still satisfying containment), the same needle smuggled into an `env:` block scalar with `run:` rewritten, a step-level `continue-on-error: true`, and a step-level `if: false`. Count-before-containment ordering is what makes this shape airtight rather than merely deeper: any line that can satisfy the whole-line-anchored `run:` containment is a strict SUBSET of the `run:`-key count regex, so an `env:` smuggle bumps the count to 2 and fails there first, and with the count at 1 the scanned line IS the effective one.

Suite 157 → 169 PASS. Then the class moved OFF the key axis entirely, which no depth of key enumeration could ever have seen. YAML continues a PLAIN scalar onto any line indented deeper than its key and folds the newline to a space, so inserting `          || true` (10 spaces) directly under a step's `run:` line makes the effective command `bash scripts/check-npm-audit.sh . || true` while the `run:` line stays **byte-identical** — the whole-line-anchored containment still matches, the `run:`-key count still reads 1, and the line was never examined because it is not key-shaped. The class is live at ALL NINE cut step sites — quality-gates.yml's three audit steps (web, mcp-server, root), cd.yml's three, ci-success's verifier, and the suite's own two CI steps — which is the number that governs the pin's coverage obligation. Round 21 measured five of them, each **169 PASS / 0 FAIL**, PyYAML confirming the folded value (two of quality-gates.yml's three audit steps, cd.yml's root audit step, ci-success's verifier, and the suite's own CI run step); the test seat later measured all nine and found every one live, so the five was a sample, never the blast radius.

The effect is identical to `continue-on-error: true` — the very thing the suite pins the ABSENCE of at each of those steps — reached through the value instead of a key; on cd.yml it is worse than non-blocking, since the security job genuinely exits 0 and `needs.security.result == 'success'` becomes true on its own terms, so both deploy jobs proceed past a red audit. Width adjustment cannot close it: indentation is the attacker's free choice (10, 12 and 14 all parse and all measured 169/0; only 8 is caught, and an 8-space continuation is invalid YAML GitHub would reject anyway — a void case). Fixed by enumerating the exact set of LINES rather than keys: key lines stay value-stripped so a cosmetic step rename is still green, and every other non-empty line is listed VERBATIM, so a continuation lands as an unexpected element at ANY indentation because it is a line that was not there before. Bonus coverage the key-set form missed — verbatim listing also pins the two real non-key lines, the shellcheck step's `run: |` body and ci-success's `NEEDS_JSON: ${{ toJSON(needs) }}`, so rewriting the verifier's INPUT to something it reads as "no jobs" is caught too.

The same continuation arm was added to ci-success's own job-level `if:` pin (its cut block must be exactly one line) so the round's new pin did not ship with the defect it was written to fix.

## The general lesson: an enumeration of KEYS says nothing about VALUES

The general lesson, which is why this recurred at four successive levels: an enumeration of KEYS constrains which keys exist and says NOTHING about what they are worth, so wherever a VALUE is load-bearing, a containment pin on its line does not prevent that value being EXTENDED from the line below it.

## Scope of line enumeration, as first shipped

Scope, deliberately: line enumeration is applied at step level and to that one `if:`, NOT at job level — the job-level load-bearing values are the deploy/ci-success `if:` clauses (whose pins already claim PRESENT-not-EFFECTIVE, so a continuation falls inside a stated residual) and the caller's `uses:` (a folded path stops resolving and the workflow fails to load — fails CLOSED), and cd.yml's deploy `if:` blocks are legitimately multi-line; logged on PF-1012 so the decision is revisited rather than inherited. Suite 169 → 170 PASS.

## …and why that scope was wrong

That scope decision was WRONG and measurement overturned it in the next round, which is the sharpest lesson in this whole entry: **a stated limitation only covers what its REASON covers.** "PRESENT-not-EFFECTIVE" is true of a REWRITE and says nothing about a CONTINUATION. cd.yml's deploy `if:` is a `|` LITERAL block scalar, so appending `      || true` beneath it extends the block's VALUE — every original line, `needs.security.result == 'success'` included, stays byte-identical while the guard resolves to `... || true`. Measured GREEN at 170/0 at BOTH deploy jobs, i.e. a red audit deploys to production. Count pinning is provably insufficient here, unlike at step level: rewriting the LAST clause line to `(...) || true` keeps the line count identical AND leaves the security containment intact, so both deploy `if:` blocks are pinned VERBATIM. The `uses:` exemption was unmeasured assumption too — inserting `      decoy.yml` folds the caller's path to `./.github/workflows/quality-gates.yml decoy.yml` at 170/0 green (whether GitHub's loader then fails closed was never tested, and "it probably fails closed" is not a pin), so its cut block is count-pinned to exactly one line.

These blocks get NO value or comment stripping, the opposite of the step-level enumeration: inside `if: |` every line IS the load-bearing value and a `#` is literal scalar content, not a comment.

## Steps the pins never named

The round after that moved the class OFF the value axis as well, to the one thing every pin so far had in common: each scopes to a block it NAMES — the three audit steps, the verifier step, the two self-defense steps. The security job's OTHER steps (`- uses: actions/checkout`, `- uses: actions/setup-node`, both `- run: npm ci`) were unconstrained, and two one-line payloads ran arbitrary code BEFORE the first audit at 170/0 green in BOTH workflows: an ADDED step whose `run:` writes `exit 0` over `scripts/check-npm-audit.sh` (PyYAML placed it at step 3, audits at 4/6/7), and an EXTENDED existing `- run: npm ci && printf 'exit 0\n' > scripts/...` (step count unchanged at 11). ## Rounds 27-29: defects in the suite's own machinery

Two later rounds closed defects in the suite's OWN machinery rather than in what it pins, and both are the same lesson at different depths. Round 27 had scoped the suite's two SIGPIPE hygiene locks to a heredoc-filtered copy so fixture PAYLOAD could not trip them — but the filter treated ANY line matching `<<[ \t]*'IDENT'` as an opener, so a leading-`#` COMMENT carrying the token, or the same token inside an ordinary double-quoted STRING, opened a swallow bash never performs, and a delimiter that never reappeared alone swallowed to EOF. It was LIVE, not theoretical: the comment above the `expected_steps_1` fixture spells that fixture's own delimiter, and it hid the 39 lines after it — including a real opener — from both locks, so the committed file already mis-parsed itself while its comment claimed no executable line could hide behind the filter. Fixed by recognizing only line SHAPES that are unambiguously real openers in bash, plus fail-closed arms for an unrecognized shape and for a delimiter still open at EOF; a tag whitelist would NOT have closed it, since the live mis-parse uses a legitimate tag.

Round 29 then found that the same regex was doing two jobs at once — opener DETECTOR and error TRIGGER — so every heredoc spelling outside it (`<<"IDENT"`, `<<-'IDENT'`, a bare or backslash-escaped delimiter) was INVISIBLE rather than rejected, and bash's payload for it was scanned as code; a payload line matching a recognized shape then opened a swallow in awk that bash never opens, measured GREEN at 188 PASS / 0 FAIL via three spellings, each hiding a genuine lock violation. The polarity of the whitelist was right; its INPUT was wrong. Widening the DETECTOR to every spelling bash honours moves an unmodeled form from invisible to REJECTED — the fail-closed state the design already intended — and detection runs on a copy with `<<<` here-strings stripped, which is cheaper than a preceding-character guard (measured: the extra captured character shifts awk's RSTART/RLENGTH and corrupts the tag extraction).

## The durable lesson: keep the detector separate from the trigger

The durable lesson, and why this recurred one round after the other: **a whitelist of what may open a swallow says nothing about which lines the whitelist is consulted for** — keep the detector and the trigger separate, or a blacklist with one entry hides inside the whitelist.

## Round 30: evidence produced BY the audited thing cannot fail

Round 30 then turned the idiom on the suite's own machinery for the second and third time, in the SAME 20-line block, and each half is a distinct lesson. The first is the sharpest member of the vacuous-assertion class yet: round 27's filter self-check could not see a reversion of the FILTER. `SELF_EXEC_DIAG` is populated only from what the awk program writes to stderr, so a program carrying no stderr-writing logic can never populate it, for ANY input — the `elif [ -n "$SELF_EXEC_DIAG" ]` arm is structurally UNREACHABLE the moment the filter regresses to the pre-round-27 naive form, and what remains is incidental: whether the newly-swallowed region happens to hold a live violation for a lock below to trip on. Today it does not. Measured at the round-29 HEAD: swapping ONLY the awk body back to that form — touching nothing else, not even the surrounding `SELF_EXEC`/`SELF_EXEC_DIAG`/if-elif-else scaffold — left the suite at 192 PASS / 0 FAIL, including the very line meant to catch it; it stayed green with a hygiene violation planted inside the region that form swallows, so the reversion does not merely go unpinned, it silently RE-OPENS the comment/string/EOF hole round 27 closed; and dropping the END still-open-at-EOF arm alone was green the same way.

The degenerate `{ print }` filter is the one member of the class that already failed, and only by accident — with no swallow at all the fixture payload reaches the locks and one trips. Fixed with the sixth application of the exact-line-set idiom, count pin first (a later `SELF_EXEC_FILTER=` wins under last-assignment-wins while the pin reads the dead first one — measured green pre-fix) then the body pinned line-for-line. The generalizable rule, and the reason two consecutive rounds landed inside this one block: **an assertion whose evidence is produced BY the thing it audits cannot fail when that thing is removed** — stderr silence proves nothing about a program that has no stderr path, exactly as a count pin passes vacuously on a block the cut read nothing from. Prefer a pin whose evidence is the artifact's own text over one that consumes the artifact's output. The second half is round 29's own widening reopened one level down, and it is the clearest instance yet of **a fix that moved the boundary instead of removing it**: round 29 correctly separated the opener DETECTOR from the error TRIGGER, but kept modelling the delimiter as a C identifier in all four alternatives, while POSIX makes `here_end` an arbitrary WORD (`io_here : DLESS here_end`).

A digit-, dash- or dot-leading delimiter is honoured by bash and is not an identifier, so it was INVISIBLE to the detector — not rejected — and the round-28 exploit reproduced verbatim through the widened code. Seven spellings measured at the round-29 HEAD (bare, single-quoted, double-quoted and backslash-escaped `1ZEOF`; `<<-"1ZEOF"`; `<<'-ZEOF'`; `<<'.ZEOF'`), each GREEN at 192 PASS / 0 FAIL, each `bash -n` clean, each with its hidden lock violation EXECUTING at runtime while absent from the filtered copy, neither fail-closed arm firing, and the affirmative "parsed every heredoc opener" PASS still printing; opening the swallow early dropped 410 lines from the locks' scope, still green. Fixed by deriving the class from the grammar instead of enumerating it — a WORD is everything up to the first character that ends one — which is why the in-code claim that round 29 had covered "every heredoc spelling bash honours" was itself corrected in the same commit: an enumeration that calls itself exhaustive is the thing to distrust.

All five literal `<<` in the awk program must be respelled `[<][<]` alongside it or the widened pattern matches the program's own source lines and self-trips (measured: partial respelling gives 191/1 on an otherwise clean tree). Every one of the seven is now RED with the shape diagnostic, while the same violation planted with no swallow at all stays RED via the lock itself — the control that keeps those rows from being vacuous. ## Round 31: pin the link the evidence flows THROUGH

Round 31 then closed the last two members of the family, both again in the suite's own machinery, and both are one lesson stated twice. First: **a pin protects the link it NAMES, not the link the evidence flows through.** Round 30 pinned `$SELF_EXEC_FILTER`, but the two hygiene locks read `$SELF_EXEC`, one assignment downstream, and THAT hop had no pin — a single `SELF_EXEC="…"` inserted after the assignment measured 194 PASS / 0 FAIL, `bash -n` clean, with a planted hygiene violation executing at runtime and both affirmative pin lines still printing (the `-z` arm is satisfied by any non-empty string, and `SELF_EXEC_DIAG` is computed separately from the real filter so it stays empty, so neither fail-closed arm fires). Second: that pin's own guard modelled a byte pattern rather than bash's assignment grammar — the count pin (`grep -cE "^SELF_EXEC_FILTER="`) and the body cut (`/^SELF_EXEC_FILTER='$/`) both anchor at COLUMN 0, while bash accepts an assignment with a leading space, a leading tab, under `declare`, under `typeset`, or after a `: ; ` separator.

All five respellings measured 194/0 GREEN with a naive filter in force while the column-0 baseline of the identical mutation went red, so the guard was a blacklist of one spelling. That is the fifth appearance on this branch of "a convenient byte pattern standing in for a language construct" (after `here_end`-as-C-identifier in round 29), which is why the fix stops widening patterns: the column-0 count pin and body cut are DELETED, replaced by a pin on the EFFECTIVE RUNTIME VALUE (`assert_block_lines_exact "$SELF_EXEC_FILTER" …`). Last-assignment-wins makes whatever the variable holds at the pin the program that actually ran, so every spelling is covered by construction with no grammar to model, and the count pin — which existed only to make the column-0 cut trustworthy — becomes unnecessary rather than merely widened. The downstream hop is closed by a VOLUME pin on `$SELF_EXEC` (`total - kept == 326`), which is evidence that is the artifact's own text rather than output consumed from the audited program — round 30's own lesson applied to round 30's own blind spot.

`readonly SELF_EXEC_FILTER` / `readonly SELF_EXEC SELF_EXEC_DIAG` is layered on as a CONTROL, not as the fix: under `set -uo pipefail` with no `-e` a later assignment errors, does not abort, and the ORIGINAL VALUE IS PRESERVED, so every reassignment vector is a no-op — fail-closed by preservation rather than by detection. Verified in two batteries of six vectors plus a clean control each (fix as written; then again with BOTH `readonly` lines deleted): all twelve vectors RED, both controls GREEN, which is what proves the two pins are the detection layer and `readonly` is defence in depth. ## Round 32: the filter's INPUT

Round 32 then closed the last member of the family, and it is the same lesson as round 31 reached from the opposite direction: **round 31 pinned what the filter IS; round 32 pins what the filter is CONSULTED FOR.** Round 30's heredoc shape whitelist is LINE-LOCAL and bash's parse is not — whether `<<'JSON'` is a redirection depends on quoting state carried in from earlier lines — so a line can match a listed opener shape byte-for-byte while being pure string content to bash, which makes the in-code claim that "a shape is only listed here if a line matching it IS a heredoc opener, which is what makes the exclusion provable rather than assumed" false as applied. The exploit is one contiguous insertion touching no existing line: an assignment spanning three lines (the quote inside `<<'` closes the string the first line opened), then the hidden code, then a real heredoc whose terminator also closes awk's phantom swallow — `bash -n` clean, balanced to both readers, and the region between is dropped from `$SELF_EXEC` so both hygiene locks scan past it.

The security seat measured it at 976e3f3c, which PREDATES round 31's volume pin, so it was re-measured at HEAD before being accepted OR dismissed — and the result split the difference, which is why re-measuring rather than guessing is the rule: the volume pin DOES fire on the mutation as written (dropped 365 vs the pinned 361), but that is arithmetic, not detection. One extra line recomputing the expected drop restores **GREEN 194/0 with the violation executing**, and a JSON fixture reformatted four lines shorter would compensate with no pin touched at all. So the finding stands, downgraded from a 1-line to a 2-line attack, and the durable lesson generalizes past this file: **a single number is something an attacker can recompute — prefer an exact line set over an arithmetic invariant.** Fixed by the seventh application of the exact-line-set idiom (after column-0, 2-space, 4-space, step-key, step-line and job-steps): the exact ORDERED set of lines that can open a swallow, 34 today.

A phantom opener is by construction a line that was not in that list, so it lands as an unexpected element whatever it spells, and ordering catches the one case a set would not — a phantom spelled IDENTICALLY to a real opener, which arrives as a duplicate. No bash quoting grammar is modelled anywhere, which is the whole point: rounds 28-31 each widened a byte pattern and each was defeated by the next spelling, so the fix stops describing what an opener looks like and enumerates what the openers ARE. Two mechanical details are load-bearing. `<<` is respelled `@@` on both sides (the observed list via `sed`, the expected payload written with `@@`) so the expected list can quote the real openers verbatim without matching the shapes itself — the self-match problem that also killed the simpler idea of pinning the 14 raw-file lock-pattern matches directly, since storing them in a heredoc doubles the count.

And the two mirror patterns must spell theirs `[<][<]`, the same technique the awk program uses on its own source, or they trip the detector's fail-closed diagnostic arm. Three other alternatives were rejected on the record: tracking quoting state across lines in awk (another byte-pattern approximation of a language construct — the treadmill this branch keeps escaping); asking bash itself which lines are code (no bash facility emits a code/data line map — `bash -n` gives none, and `set -x`/`BASH_XTRACEFD` is runtime-only so it misses unexecuted lines); and quote-parity counting (already defeated by backslash-escaped quotes in round 26). Verified in two batteries of six rows each: battery A (fix as written) is clean GREEN 195/0 with every phantom RED — the exact mutation, the mutation with the volume pin compensated, a phantom spelled identically to a real opener, and a phantom using the other recognized shape; battery B (the new assertion deleted) has all three compensated rows GREEN with the violation executing, which is what proves this pin rather than the volume pin is doing the work.

Every mutant `bash -n` clean. Honest ceiling, unchanged from every pin here: any pin whose expected value lives in the same file as the payload is defeated by a coordinated same-file edit — what round 32 buys is that the attack is no longer one contiguous insertion with no existing line touched. Suite 194 → 195 PASS.
